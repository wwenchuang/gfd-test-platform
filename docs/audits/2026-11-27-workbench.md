# 测试工作台的操作路径与 Agent 接入

## 同事从哪里开始

首次登录进入「测试工作台」。有上次访问记录的同事返回原页面。打开报告链接直接进入对应批次。执行回归时按设备和应用选择已发布的基线。报告展示失败步骤和证据。侧栏的「调查与缺陷」可直接打开失败处理、调查记录和缺陷草稿。环境、权限和 Token 费用归到配置。脚本编辑、调试与同步适合维护用例时展开。

## 盘点范围与决定

使用工作台当前登录账号逐项打开 26 个导航入口和接口平台 15 个页面，另核对首次登录落点。走查看路径时限制了写请求。此项验证页面是否可达、折叠层数、页面错误和横向溢出。项目配置写入、真机、性能负载、真实飞书回执及企业业务日志各自需要独立证据。

| 能力及入口 | 对应同事的任务 | 本轮处理或验收边界 |
| --- | --- | --- |
| 工作台首页、最近回归 | 对照需求、结果和待处理问题 | 原首页跳到选手机。改为首次进入任务首页，保留报告直达及原页面恢复 |
| 开始测试、用例库、我的测试 | 选择应用、设备、核心或完整基线，检查原始执行 | 复用版本化快照、设备预检、报告与选择器。修复 iOS 专属基线的单值平台字段沿用 Android 的错误 |
| Monkey、UI 定时任务 | 按时长运行稳定性检查、编辑或触发定时回归 | 两者分别保留可见入口。读取配置和历史记录，现场不改已有计划 |
| 埋点测试 | 上传方案、对照实际请求及回执 | 独立页与首页入口保留。缺采集证据应显示待实测 |
| Agent 工作台、运行记录、待我确认 | 交给 Agent 调查，查看选择的工具与待处理任务 | 调查入口移出高级工具，选择后可恢复。高权限操作沿用原权限 |
| 失败处理、缺陷草稿、执行报告 | 定位失败、看原始断言、登记产品缺陷 | 失败处理与缺陷草稿常显。历史执行报告按需展开。需求批次另有飞书项目建单回执 |
| 用例资产、AI 生成、录制、脚本编辑 | 从需求建用例或维护既有脚本 | 首页接收需求，可用已验收映射直接冒烟。没有映射时保留需求与验收条件供设计 |
| 调试执行、同步 Sonic | 先调试、再发布资产 | 保留为高级操作，打开深层页面时展开其父级 |
| 成员与权限、模型配置、应用配置、执行环境、群通知、环境体检、Token 用量与费用 | 管理权限、资源、费用与通知 | 集中到配置。飞书群通知与飞书项目缺陷分开记回执 |
| API 首页、任务、资产、用例、基线 | 整理接口、生成或运行业务断言 | 统一入口保留原项目和环境权限。API 已有回归与巡检，本轮需求接收器先接真机冒烟 |
| API 定时、执行记录、报告 | 检查每日回归和上次失败 | 保留既有执行和报告详情。页面切换要等目标视图完成加载再取证 |
| 性能场景、执行、定时、分析、报告、节点 | 预检、组织负载、对比指标 | 保留独立执行与环境门禁。本轮导航验收没有对共享服务加压 |
| API 项目环境 | 配置运行环境和项目通知 | 维持项目级管理。业务日志源须由开发提供服务名、环境及只读入口 |

## 一条需求怎样走到结果

1. 飞书项目同步器只读指定空间、工作项类型和已提测条件。取得编号、版本、验收条件和业务场景后写入需求记录。重复轮询同一版本复用记录。也可以在测试工作台登记，页面保留实际来源。
2. 先找明确绑定的需求版本，再找已配置的业务场景。匹配后检查应用权限、基线快照、目标系统和设备可用性，每个平台最多三条冒烟。没有映射、版本不符、设备不可用时显示具体状态。待设计的用例走现有设计与发布流程。
3. 执行批次保存版本、尝试、Runner 回调和报告。需求卡可以打开对应报告。仅提交批次时不显示测试通过。
4. 失败后调用现有调查 Agent。它可按证据选择步骤、请求记录、历史运行等只读工具。将本次失败和运行证据交回报告。建单门禁独立核对当前用例版本、失败步骤、诊断和执行终态。设备离线和上游模型服务异常由调查处理。
5. 只有飞书项目成功回执内的工作项号才能展示为已登记。超时或丢回执，按唯一关联标识查回，暂未确认时保留待核对。同一需求版本的相同缺陷避免重复提交。
6. 日志采集按服务及五分钟窗口聚合，记录可见范围、日志命中和恢复。管理员在首页看更新时间与状态。采集过期、源不可用和未观察到错误分开呈现。默认在工作台内查看；额外群通知取决于实际接收群配置。

## 外部做法如何落到现有业务

GitLab 将测试差异与原用例关联，便于从合并请求追到执行结果。本平台采用需求版本、批次、用例步骤和缺陷回执之间可追溯的关联。[GitLab 单元测试报告](https://docs.gitlab.com/ci/testing/unit_test_reports/)

Prometheus Alertmanager 按归并规则处理通知与重复告警。本平台按服务、时间窗和告警状态归并，监测恢复，保留投递不确定状态。[Prometheus Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)

Anthropic 的实践区分可预测的工作流和可自主选工具的调查。这里让 Agent 根据新证据决定查什么，平台负责版本、执行范围、预算和外部写入，并保留执行轨迹。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

## 接入资料与下一轮验收

| 谁提供 | 需要什么 | 接好后怎么判定成功 |
| --- | --- | --- |
| 飞书项目管理员 | 测试空间链接、可试点的需求及缺陷类型、「进入测试」状态、验收条件字段、缺陷证据字段。插件服务身份应能读需求、查缺陷及在指定项目建缺陷，凭证在服务器填写 | 读取真实工作项，更新同一版本两次只触发一次批次；对已确认失败创建一次缺陷，在飞书项目查回相同工作项号 |
| 开发或运维 | 智小白 3D 测试环境的日志系统、服务或索引名、只读接入方式、一次已知错误的时间及请求标识 | 由运行标识找到同一条业务错误，有界窗口内触发和恢复各一次；无权限时显示来源不可用 |
| QA | 配置首个业务场景的已发布 Android / iOS 冒烟及可用测试机；如启用业务告警，指定接收群和环境 | 核对两端各自批次与原始断言。不同环境日志及工单分别统计 |

现场测试、受控回放与租户待配置项应分开记录。智能判断效果后续用已经人工定位的历史问题评估，包括误提单数、有效证据比例、调查时间与 Token 费用。尚未对照时不填写收益数字。

- 通过工作台首页手工登记已有「套件专区」需求。OPPO Reno9 的「主题配套套件介绍」10 步通过，iPhone 13 的对应基线 9 步通过。两份报告均已从需求卡实际点开，核对用例名称、通过状态及截图区。[Android 报告](http://101.34.197.12:8088/task-manager.html?ui_batch=uib_948d683c897a48cdb26f5d112fea543f) · [iOS 报告](http://101.34.197.12:8088/task-manager.html?ui_batch=uib_b7a52f4c154646bd90227412036f8bec)
- 在另一条历史 iOS「打印记录查看」报告点击 AI 分析。Agent 查询失败步骤、Runner 轨迹、设备日志关联和历史通过记录。点开两份引用证据，失败断言要求设备尾号 4F2A，Runner 日志记录页面显示 F90A。为何选中 F90A 仍缺证据。无对应网络轨迹或打印任务。[失败报告与调查证据](http://101.34.197.12:8088/task-manager.html?ui_batch=uib_10ccab55bb1c4dcbaacfc7d133eaced0)
- 页面检查覆盖 41 个入口和首次登录。调查与缺陷入口从一至两层折叠调整为直接可见，刷新 Agent 页面能恢复现场。390 像素宽度下验证首页无整页横向溢出。重新等待用例资产、录制和接口执行列表加载，三者均显示对应视图。
- 工作台真实服务的日志定时器已运行。按服务保存最近 48 小时的脱敏计数；调查只引用与执行区间重叠的完整窗口。时间重叠支持进一步排查，不能证明某个请求导致错误。为历史 iOS 失败补查其真实执行窗口，四个工作台服务均有完整采集，错误行数为零。当时段无采集时报告标明缺口。
- 飞书项目读需求、建缺陷、幂等、丢回执查重已覆盖受控响应和本地权限用例。真实飞书租户端到端尚待验证。真实业务日志和外部飞书告警投递仍待接入。
