# 下一轮验证建议使用说明

在新建压测的“测试目的与可比条件 → 下一轮建议依据”填写业务目标、单轮最大增长比例和期望观察时长。吞吐目标为每秒完整链路次数（一个链路可能包含多个HTTP请求），并发目标为VU。切换模型需重新核对。三个值都是本次执行快照的一部分，不影响历史报告。

报告中的AI负责结合步骤失败、延迟及实际监控提供观察、可能原因和验证方法。下一轮可预填配置由平台策略产生，界面明确标明来源，不把AI自由生成的数字直接拿来发压。

| 本轮情况 | 下一步 |
| --- | --- |
| 未达压、节点或采样证据不足 | 修复后同压力同时间复验，计数差异沿用平台容差 |
| 失败或验收阈值未通过 | 先定位失败步骤，再同条件复验 |
| 未接服务监控、样本不足或容器缺配额 | 新建压测补齐监控后同条件复验 |
| CPU/内存高、Pod不就绪或重启 | 关联异常时间和日志排查，不将信号直接当成根因 |
| 压力机自身资源高 | 先核对压力机资源，不归因于业务服务 |
| 只读固定吞吐、目标和监控齐全且观察充分 | 按填写步长增加，不超过业务目标 |
| 已达到业务目标或完成稳定性观察 | 保留结果，不无限升压或延长 |
| 写操作、未知副作用、阶梯/突发及固定VU增长 | 人工设计下一轮及清理安排 |

资源85%为平台保守的不继续升压提示线，不是行业统一标准或业务阈值。资源监控至少3个有效样本、覆盖率95%仅是建议证据门槛，并不能证明系统容量。CPU平滑窗口及主机/容器口径仍以原监控说明为准。只涵盖选定服务实例，未监控依赖不能认为正常。

“按建议配置下一轮”只预填配置，保留原场景/环境版本、阈值和监控快照；节点需重新选择，仍要检查连通性、预检及确认启动。监控异常尚未自动联动停止，需人工干预；已配置HTTP错误保护仍按既有规则执行。AI置信度只描述当前诊断，不保证下一轮安全或达标。

历史诊断需点击“重新诊断”才会使用新策略。此操作不会重新发压。平台部署需同步后端、worker和前端，本次不需要升级Agent。真实服务监控接入前不能验收CPU/内存驱动的线上建议。
