# 性能场景当轮资源清理

新版执行使用 `k6-safe-v3`。支持一个迭代创建一个临时资源，并在本迭代结束的 `finally` 中执行一次关联清理；业务断言失败会停止后续业务请求，但不会跳过已确认归属资源的清理。清理 HTTP 请求也会计入实际请求量；失败计入业务链路失败，报告可通过清理步骤查看请求与断言。预检把清理耗时计入单轮观察时长。

配置要求：创建步骤 `scope=iteration`、`side_effect=creates_owned_resource`，声明 `cleanup_step_id`。`risk.ownership_variable` 指定创建响应 JSON 中必需提取的唯一 ID，不允许默认值、不允许其他步骤覆盖。关联 `cleanup_once` 必须与创建使用同一服务，并使用 `DELETE /resources/{{本轮ID}}` 形式的路径，不允许 path_params 覆盖 ID 或只在请求头声明归属。ID 仅允许 1–256 位 ASCII 字母、数字、下划线与连字符，或 0–9007199254740991 的整数；数字在预检中规范为十进制字符串。拒绝空白、点、斜线、问号、井号、百分号及编码片段，避免查询串/片段或重复解码改变删除路径。

每轮开始清空归属 ID；只有本轮创建请求返回 2xx 且确实提取到有效 ID 后，才允许清理。预检从该响应逐项独立提取；其他必需字段缺失仍判失败，但不会丢失已经确认的归属 ID，也不会再次发送创建请求。创建超时、连接断开、结果未知或 ID 缺失时，不重发创建、不猜测 ID，不使用上一轮 ID；预检显示资源归属未知并阻止发压，实际执行计为失败，需要人工核对服务端资源。写请求最多等待 10 秒、不跟随重定向，预检与实际脚本均应用此限制。

仅支持上述有界流程。`setup_once`、节点/VU 初始化写入、更新已有资源、多资源创建清理、独立清理和自动 polling 均明确拒绝；不能把固定 sleep 当作异步终态验证。节点断电、失联、进程强杀后没有持久补偿队列，不能保证 finally 完成；人工停止前也应准备资源核对方案。Agent 现有停止流程发送 SIGINT 后最多等待 10 秒再强杀，这一边界没有改变。

历史 v1/v2 编译脚本仍按原版本生成，v2 使用完整保留副本并有脚本字节测试；但含写/清理或全局 setup 的未启动旧执行会在启动与领取时被阻止，应创建新版执行。旧只读执行可以继续按原版本运行。本批不升级 Agent，不改变历史报告或历史脚本内容。

本地验证使用 Node 执行生成脚本，以及真实 k6 0.52.0 对回环 HTTP 服务：验证第一轮成功清理、第二轮创建断开不误删旧 ID，以及清理返回 500 时业务链路失败。夹具不访问线上业务。真实 k6 检查可用 `K6_BINARY=/path/to/k6 .venv/bin/python -m pytest tests/api_testing/test_load_lifecycle_v3.py` 重复执行。
