# 性能测试使用与交付说明

本版在已有场景、节点、执行和报告上补齐可配置监控、压力机运行资源、负载目的、保护停止、Word/Excel 导出、多轮比较和人工参考基线。页面实现与上线验收分开：本地检查通过不意味着真实业务 CPU 已接通，也不意味着系统容量已验证。

## 一次压测怎么操作

1. 工作台选择应用及接口版本。在“性能场景”新建或编辑场景，选择真实接口和业务断言。编辑会创建新版本，不改写历史执行。高级配置支持保留和编辑请求、提取变量、断言、数据集；修改 JSON 后先“应用”，格式错误时不能跳过。
2. 数据集选择已上传数据，或导入 CSV/JSON。页面只展示字段和行数，不展示凭据。不要把真实打印、短信验证码、支付或删除历史业务数据直接复制成高并发场景。异步导入、切片需要验证最终状态，提交成功不等于业务完成；当前没有通用自动补偿编排器。
3. 创建压测：记录本次目的、业务版本、账号/数据规模、缓存条件与清理安排；选择目标环境、并发或吞吐、时长及验收标准。目的只是说明，不会自动选择安全负载。阶梯负载可按阶段修改时间和目标，支持预热、稳态、恢复模板。
4. 按预估选择压测节点。每台可分配容量为 `max(0, min(硬上限, 平台软上限, 有效校准容量) - 占用)`，还受进程、时长及在线状态约束。800+800 校准不代表一定能分配1600；在节点页调整软上限，不能越过硬上限或校准保护。
5. 勾选本次服务监控。可直接新增配置后复用，设置必选/可选及前后观察时间。源地址首次授权需要管理员；普通执行不能任意探测网络。配置被冻结到执行，后来修改不会改变历史报告。
6. 依次检查目标连通性、单用户预检、开始执行。它们各自返回结果，不是一个按钮等于全部通过。启动前检查新鲜监控样本；必选监控没有样本时不应带病开始。列表自动更新，完成后等待监控观察窗口结束再导出正式报告。
7. 报告先看结论、目标是否达到、质量标准和证据完整度，再看接口、业务链路、服务资源、压力机资源及 AI 建议。下载 Word 给汇报使用；Excel 保留数字明细用于复核。鉴权通过现有登录会话，不把令牌放在下载地址。
8. “性能分析”选择2–5轮，指定参照，核对环境、数据、负载和监控口径。必要时人工采纳参考基线并设退化阈值；旧参考只退役，不被新执行覆盖。删除来源执行也不会删除冻结证据。

## CPU 和其他资源在哪里看

| 观测对象 | 当前支持 | 要求与限制 |
| --- | --- | --- |
| 被测整机 | CPU、内存、网络收发、磁盘吞吐、IOPS、空间、平均读写延迟 | Prometheus + node_exporter；逐设备/挂载点展示，不能冒充单个业务服务 |
| 独立容器 / Pod 内各容器 | 实际 CPU 核数、内存 working set；有确定配额时 CPU 占比 | 已有 cAdvisor/kubelet 指标；精确标签；无限额时不编造占比 |
| PostgreSQL 数据库 | 指定数据库后端连接、提交/回滚速率 | 已有 PostgreSQL exporter；连接包括空闲连接，事务不是业务 TPS |
| 发压节点 | 运行时 CPU 核数、内存、可确认的配额及占比 | Agent 0.1.5；cgroup 包含 Agent 和子进程，进程回退仅 k6，不能当成被测服务 |

缺失、未接入、不适用分别表达。首次 CPU 采样没有差分、零 I/O 没有平均延迟、无限内存没有百分比，这些情况都是未知，不填0。真实业务源需要可访问地址、只读凭据（若有）和实例标签；旧附件的服务名和规格不会自动成为当前配置。无现有监控时见 [采集部署包](../deploy/load-monitoring/README.md)。

## 常见指标与判断

| 名称 | 意思 | 易误读之处 |
| --- | --- | --- |
| VU | 同时执行脚本的虚拟用户 | 不等于请求次数、真实在线用户总量或每秒请求数 |
| RPS | 每秒 HTTP 请求数 | 一次链路可能发多个请求 |
| 迭代 / 事务 | 一次完整场景脚本执行 | 开始数、完成数、成功数是不同计数 |
| P95 / P99 | 95% / 99% 的已采集耗时不超过此值 | 不直接平均各节点、各窗口分位数；缺失样本影响可信性 |
| HTTP 错误率 | HTTP/网络失败请求占比 | HTTP200仍可能业务失败 |
| 业务断言失败率 | 已执行断言的失败占比 | 没写或没执行断言不代表业务成功 |
| 链路失败率 | 有失败步骤的完整链路占比 | 与 HTTP 失败率分母不同 |
| IOPS | 每秒磁盘读写操作次数 | 不是吞吐字节数，平均 I/O 延迟不是请求P95 |
| 退化百分点 | 两轮错误率之差 | 从1%到2%是增加1个百分点，也相对增长100% |

固定吞吐控制每秒开始迭代，不承诺“精确发20个HTTP请求”。调度边界、链路多请求和在途完成都需要核对。新阶梯吞吐保留各节点每阶段开始数和结束边界外开始数，不能用一个节点多发掩盖另一个未发；阶梯VU尚无按阶段对齐的实际并发证据时保留证据不足。

请求计数与耗时样本按同节点/步骤全程比较：差值同时不超过2条且不超过较大计数10%，只提示统计风险，仍保留原数；不扩大为允许节点失败或损坏数据。通过测试并不是系统最大容量结论，短跑也不能证明长期稳定。

## 保护停止与报告建议

HTTP错误保护按各发压节点累计HTTP错误率判断，在宽限时间之后触发；不是“最近一分钟滑动窗口”。一个节点在保护策略启用时失败，平台要求其余节点停止并保留最后指标，自动停止与人工停止分开归因。停止发压不能撤销已经提交的后台任务，清理必须由业务场景设计负责。不能依赖该功能给生产无限制加压。

AI结合当前冻结证据提供观察、可能原因、验证方法与行动建议；没有服务日志或数据库证据，不能断言SQL瓶颈或内存泄漏。AI不可更改确定性统计或阻止基础报告生成。导出仅附带与当前证据匹配的已完成诊断。

## 本版边界与后续验收

本版实现手动多轮对比、人工性能参考基线和手动退化核对。没有启用定时性能发压、自动发送退化通知、跨Pod聚合、Pod就绪/重启统计、其他数据库专用模板、混合业务权重或通用异步补偿。这些不能用现有按钮或接口数量冒充完成。每日API功能基线与性能参考基线是不同用途，自动修复草稿不得自动采纳到固定参考。

正式容量验收前应确认目标业务吞吐/延迟/错误标准、账号及数据规模、流量模型、测试环境资源和业务副作用；先小流量核对，再逐阶梯测，最后独立做稳定性测试。多轮条件不同会显示原始数值和差异原因，而不直接宣布性能提升。

## 升级顺序

先部署本分支平台：安装 requirements-api-testing.txt 的依赖、按项目迁移流程运行到0012、更新前端产物并重启API及Celery worker/beat。再升级参与压测的Agent。旧冻结v1脚本仍按原编译器验证哈希，新执行使用v2；不要只升级Agent而保留旧平台。

Agent源码升级包无需Git，不含令牌、.env、数据卷或镜像，升级仍需可用镜像源。包上传到 `/opt` 后逐行执行：

```bash
cd /opt
sha256sum -c midscene-load-agent-0.1.5-upgrade.tar.gz.sha256
tar -xzf /opt/midscene-load-agent-0.1.5-upgrade.tar.gz -C /opt/midscene-load-agent
cd /opt/midscene-load-agent
LOAD_AGENT_IMAGE=midscene-load-agent:0.1.5 bash deploy/load-agent/upgrade.sh
bash deploy/load-agent/check.sh
```

平台确认真实Agent版本、心跳和校准后，再做小流量执行。升级不等于业务服务CPU自动接入；网页仍需配置实际监控源并对账。
