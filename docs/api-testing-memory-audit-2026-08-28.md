# API 测试平台内存与 Sonic 恢复专项记录

## 现场证据

- 宿主机总内存约 7.44 GiB，无 Swap；Sonic Java 容器常驻合计约 1.7 至 1.9 GiB。
- 2026-08-27 两次全局 OOM 直接杀死 `midscene-task.service` 的 Python，匿名 RSS 分别约 5.04 GiB 和 4.63 GiB。
- 2026-08-28 再次点击基线“检查断言”后，Python RSS 从约 263 MiB 上升到约 2.19 GiB；客户端停止等待后，服务端线程仍继续执行。
- 用户提供的最新 `top/htop` 中，主 Python 进程启动约 12 秒即占 2.2 GiB。列表中的同 RES Python 行是同一进程的线程，不是多个独立后端。
- Eureka 此前退出时 Docker 重启策略为 `no`。已有 `configure-sonic-restart.sh`，但旧版 `update-main-server.sh` 只提示策略，没有调用该脚本，因此部署不会自动写入恢复策略。

## 风险分级与处理

### P0 已修复

1. **基线断言审计加载全部历史证据**
   - 活动基线改为逐条分页读取，每条会话结束后释放 ORM 与 JSONB 对象。
   - 最新执行尝试使用 PostgreSQL `row_number()` 只加载每条证据的最后一次尝试。
   - 不再复制整份历史响应。超过 1 MiB 的字符串响应不做完整 JSON 反序列化，只从有限首尾样本提取顶层 `code/success`。
   - 审计仍只读，不执行接口、不自动改基线。

2. **API 执行器按每个子用例重复加载整次执行证据**
   - 子结果持久化改为按主键读取单条，不再形成 O(N²) 全证据加载。
   - 依赖结果只保留下游实际引用的提取变量，不在内存中保留全部请求、响应和断言证据。
   - 执行收尾用 SQL 聚合状态计数；未完成项只加载轻量列。

3. **执行历史、报告和飞书通知加载完整证据**
   - 执行列表和批量归档只返回轻量摘要，`sanitized_result` 使用延迟加载并禁止误触发。
   - 报告失败诊断改为用户展开时单条加载，不阻塞报告首屏。
   - 飞书通知只加载展示所需的执行元数据。

4. **报告上传与分析重复持有大对象**
   - 原始报告保持流式落盘；分片数量最多 4096，累计大小最多 300 MiB，合并过程不构造全路径列表。
   - 报告文本分析最多读取文件尾部 16 MiB；报告图片最多 2 MiB，先检查 base64 长度再解码。
   - 后台任务恢复改为逐个读取任务文件，不先构造全部 payload 列表，也不二次读取同一文件。

### P1 已修复

5. **OpenAPI 同步和 1024 接口首屏重复加载大 JSON**
   - OpenAPI 只规范化一次，稳定键在已规范化对象上重绑定。
   - 接口树只返回名称、方法、路径、标签等轻量字段；打开具体接口或创建新草稿时才读取该接口 operation。
   - 环境配置只查询来源版本的 `servers` JSON 字段，不再读取整份 OpenAPI 和全部接口。
   - 同步激活响应只返回版本元数据，不再次返回完整文档和接口目录。
   - 所有来源版本权限检查延迟加载 `normalized_document`，避免普通用例/任务请求隐式读取完整文档。

6. **无界线程和外部响应**
   - Agent 使用固定 2 个工作线程和 8 个等待位；阻塞子调用共享固定线程池。容量满会落为中文“可重试失败”，不留下假运行状态。
   - Sonic、AI Gateway、DashScope、Figma 响应在 JSON 解码前默认限制为 16 MiB。
   - Sonic 进程内缓存除 64 项上限外，增加默认 32 MiB 总字节预算；超大单项不缓存。

7. **进程隔离不足**
   - 主服务：`MemoryHigh=2G`、`MemoryMax=3G`、`TasksMax=256`。
   - API Worker：`MemoryHigh=1G`、`MemoryMax=1536M`，Celery 每子进程 50 个任务或约 768 MiB 后回收。
   - Scheduler：`MemoryMax=512M`。
   - 三个 systemd 服务分别计量，单个后台进程不能再拖垮整机和 Sonic。

## Sonic 为什么没有自动恢复

1. 当时容器策略是 `restart=no`，Docker 没有恢复依据。
2. 已提交版本中虽然存在策略配置脚本，但更新脚本没有调用它。
3. 本轮更新脚本会在每次平台部署前，对现有 `sonic-server-272-*` 设置 `restart=unless-stopped`，不会重启正在运行的容器。
4. 重启策略只处理配置后发生的异常退出，不会启动在部署前已经停止的容器。首次恢复需执行一次：

```bash
bash deploy/configure-sonic-restart.sh --start-stopped
```

此后可用下面的命令核对每个容器：

```bash
docker ps -a --format '{{.Names}}' | grep '^sonic-server-272-' \
  | xargs -r -n1 docker inspect -f '容器={{.Name}} 状态={{.State.Status}} 重启策略={{.HostConfig.RestartPolicy.Name}}'
```

## 仍需后续迁移的风险

以下问题已识别，但不在本轮用高风险兼容改造强行完成：

- `jobs.json` 是历史兼容单文件，部分恢复/取消路径仍需全量读取。直接截断会破坏历史查询，需迁移为分页数据库或分片归档后再删除旧路径。
- 完整执行详情仍允许按单次请求读取一条大证据。列表已轻量化，后续应把原始证据拆成独立分页或下载制品。
- Sonic 汇总中的长生命周期定时器和套件状态表有数量积累风险；目前由固定服务内存上限隔离，后续应迁移为持久化调度队列。
- 本地知识截图转 base64 时仍有短时副本；上传入口已有请求大小限制，后续可改为文件流/临时 URL。
- YAML 基线缓存最多 1200 文件、每段最多 2400 字符，已有数量和片段上限；后续可增加精确字节统计，但不是本次 GiB 峰值来源。

## 验收边界

- 本轮完成的是代码与部署边界修复，不能据此宣称约 240 条线上基线已经逐条升级。
- 新版本部署后先验证“检查断言”期间 RSS 不持续上升，再按“生成待复核版本 -> 调试通过 -> 采纳新基线”逐条迁移。
- 只有完成新版本调试并重新采纳的用例才计入基线修改完成数；业务失败、HTTP 失败和证据不足项不得补成功断言。
