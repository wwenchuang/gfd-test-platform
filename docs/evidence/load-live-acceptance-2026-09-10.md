## 瓶颈结论与下一步实验

本轮确认“约 1.1 秒的端到端响应时间不达标”，未证明 CPU、内存、数据库或下游已经达到容量瓶颈。服务与压力机资源利用率不高只能降低部分假设的优先级，不能单独排除配额节流、GIL/排队、网络隧道或短时尖峰。

`/demo/cpu` 使用 150 ms 墙钟时间的有界哈希循环，并非固定 CPU 工作量；不能从该演示推出真实业务最大容量。

下一步按单变量补证：

1. 先核对服务器与隧道，比较演示机本地请求、平台隧道端、两台 Agent 容器相同 `/demo/ok` 和 `/demo/cpu` 的 connect/TTFB/total 耗时；记录服务处理时间，定位额外延迟位置。
2. 当前有延迟失败，先修正/解释失败来源，在原 2 次/秒、180 秒、500 ms 阈值下复验。不能仅凭 CPU 低直接升压。
3. 达标后再设计保持至少两分钟的递增阶段，记录最后稳定—首次持续失败区间；每轮保留业务断言、实际达压、队列/429、服务 CPU quota/throttling、内存和恢复证据。受控服务 4 工作槽与 0.5 核等配额须现场确认。
4. 通过目标机本地管理员入口让 `/demo/switchable` 在预检后进入 HTTP/业务故障，验证分类、保护停止和 120 秒自动恢复；不得使用一直失败的接口绕过预检门禁。
5. AI 输入补充可审计的服务架构、依赖是否存在、主动停止原因和可用指标；缺失域必须标未知/不适用，不能凭通用排查清单宣布根因。

## 本轮发现并修复的代码问题

- 执行卡把阶梯起点当完整负载，并用不存在的 duration_seconds 显示 0 秒；改为完整曲线、各阶段总时长、零起点与分钟单位。
- 外层 HTTP 无条件将事件接口分派 SSE，挡住 JSON 轮询；现按 SSE ticket / Accept 分流，保留认证与资源授权。
- SSE 补 `X-Accel-Buffering: no`；无事件 10 秒转为串行、有界轮询；过期 ticket、迟到事件、重复 fallback 与页面卸载均有隔离。

- 首次打开报告原先 mounted 和 watcher 重复建连接；现在只初始化一次，旧报告响应不得覆盖新报告。
- 独立代码审查发现的三项 P2（迟拒并行轮询、终态分页、卸载刷新）及组件联动问题均补失败回归后修复，最终审查未发现未解决 P1/P2。
