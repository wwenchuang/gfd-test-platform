# API 性能测试使用说明

从节点校准、场景设计到报告与 AI 诊断

> V1.2 · 2026-09-04 · 适用压测 Agent 0.1.2 及以上

## 先看结论

> **要点：** 功能自动化回答“单次请求或业务链路是否正确”；性能测试回答“在一定并发或吞吐下，系统是否仍然正确、够快、稳定，以及容量拐点在哪里”。两者必须同时存在，压测不能替代每天运行的接口基线。

第一次使用建议选择无副作用的只读接口，使用“固定吞吐”，目标 1 次完整链路/秒，持续 10 秒，只选专用首选节点。先完成连通性与业务预检，再观察报告。真实打印、支付、短信、删除和高成本 AI 接口不要作为入门压测对象。

## 1. 平台四个入口与完整流程

| 入口 | 解决的问题 | 完成标志 |
| --- | --- | --- |
| 性能场景 | 把接口或多步骤业务链路、数据和断言保存为不可变版本 | 版本已保存，预检可重复通过 |
| 压测节点 | 注册 Agent、设置调度级别、校准并查看可用容量 | 心跳正常且“校准有效” |
| 压测执行 | 选择场景版本、环境、模型、目标、时长、节点和阈值 | 任务完成或停止，所有分片有明确终态 |
| 性能报告 | 查看负载目标、响应时间、错误、丢弃、资源、阈值与 AI 建议 | 确定性报告可用，AI 诊断有证据引用 |

1. 先在“压测节点”确认节点在线、版本正确并校准有效。
2. 在“性能场景”选择接口，配置变量、数据集、提取规则、业务断言和清理步骤，保存版本。
3. 在“压测执行”创建草稿，选择环境、负载模型、目标值、时长、节点和阈值。
4. 执行连通性检查与单链路预检。预检不通过时先修场景或环境，不要直接加压。
5. 启动后观察目标吞吐、P95、错误率、丢弃迭代和 Agent 资源，必要时停止。
6. 运行结束后先读确定性报告，再读 AI 诊断；根据建议设计下一轮，而不是盲目把压力翻倍。

## 2. 为什么要做压测

- 容量验证：确认给定机器和部署配置能稳定承受多少并发用户或每秒业务链路。
- 拐点定位：找到吞吐不再增长、P95/P99 明显变差、错误或丢弃开始上升的阶段。
- 稳定性验证：在预计日常或峰值负载下持续运行，发现连接池、内存、队列或外部依赖的累积问题。
- 版本回归：同场景、同环境、同负载模型对比历史运行，识别性能退化。
- 发布决策：用阈值与证据判断是否达到既定目标，而不是只凭“请求大多成功”。

> **要点：** 不要先追求“能打多高”。先定义业务目标，例如“核心查询链路 20 次/秒、P95 不超过 800 ms、HTTP 错误率低于 0.1%、业务失败率为 0”。没有目标的压测只能产生一堆难以解释的数字。

## 3. VU、QPS 与可用容量怎么理解

### 3.1 三个量不是一回事

| 概念 | 中文解释 | 常见误区 |
| --- | --- | --- |
| VU（Virtual User） | 虚拟用户；一个会循环执行完整场景的并发执行单元 | 100 VU 不等于 100 QPS |
| Iteration | 一次完整链路；可能包含多个接口、等待、提取和断言 | 一次链路不一定只有一个 HTTP 请求 |
| RPS/QPS | 每秒实际 HTTP 请求数 | 链路内有 3 个请求时，1 次/秒链路可能接近 3 RPS |
| 到达率 | 每秒开始多少次完整链路迭代 | 平台“固定吞吐”的目标是链路次/秒，不是每个接口的 QPS |

固定并发是闭合模型：每个 VU 完成上一轮后再开始下一轮，因此响应越慢，实际吞吐越低。固定吞吐是开放模型：平台尽量按目标速率启动链路；当预分配 VU 不够时会出现 dropped_iterations（丢弃迭代），说明发压端无法按计划启动全部链路。

### 3.2 页面“可用容量”的计算

```text
单节点有效容量 = min（本机硬上限，平台软上限，有效校准容量）
单节点可用容量 = max（0，单节点有效容量 − 当前占用）
平台汇总可用容量 = 所有在线、未停用、校准有效且可调度节点的可用容量之和
```

VU 和“次/秒”分别按上式计算。备用节点默认不加入自动调度，只有任务明确允许时才参与。

> **要点：** 例：某节点硬上限 500 VU，软上限 450 VU，校准容量 320 VU，当前占用 20 VU，则可用容量为 min(500, 450, 320) − 20 = 300 VU。任何一个上限更低，都会成为最终保护边界。

## 4. 硬上限、软上限和校准容量

| 项目 | 来源 | 能否人工设置 | 作用 |
| --- | --- | --- | --- |
| 本机硬上限 | Agent/Docker 部署参数与容器 CPU、内存限制 | 由运维修改部署配置后重建 Agent | 平台和 Agent 都不能突破的安全边界 |
| 平台软上限 | 管理员在平台为节点配置 | 可以调低，不能高于硬上限 | 共享机器、阶段性限流和风险控制 |
| 校准容量 | Agent 在本机运行 k6 校准后测得 | 不能手填；需重新校准产生 | 证明发压机在当前版本和资源下可持续生成的负载 |

校准只在 Agent 本机运行，不访问业务系统。当前方案逐步使用约 25%、50% 和 100% 的本机配置进行短时测量，再留安全余量保存结果。校准证据有效期为 7 天；Agent 版本、k6 版本或硬件签名变化会使旧结果失效。

> **要点：** 校准证明的是“发压机能否稳定产生压力”，不是“被测 API 能承受多少压力”。业务容量必须通过正式压测报告判断。心跳正常也只代表 Agent 在线；没有有效校准时，它仍然不可调度，所以页面可能显示 0 VU。

## 5. 校准失败与 0 VU 排查

1. 确认心跳状态为“心跳正常”。若中断，先检查 Agent 容器、网络和平台地址。
2. 展开或查看页面给出的具体失败原因，不要只看“校准失败”红色状态。
3. 确认 Agent 版本不低于 0.1.2。0.1.1 已兼容 k6 0.52 的 summary-export；0.1.2 进一步按 Docker cgroup 配额上报 CPU 核数，避免把宿主机核数误当作容器可用核数。
4. 在 Agent 服务器运行 deploy/load-agent/check.sh，检查容器状态和最近日志。
5. 升级时拉取最新代码并重新运行 install.sh；已有凭据卷会保留，正常升级不需要重新生成注册令牌。
6. 回到平台重新点击“校准节点”，等待终态；校准有效后再创建正式压测。

```bash
cd /opt/midscene-task-platform-src
git pull origin main
bash deploy/load-agent/install.sh
bash deploy/load-agent/check.sh
```

### 常见原因与处理

| 现象 | 更可能的原因 | 处理 |
| --- | --- | --- |
| 心跳正常但校准失败 | k6 输出解析、容器资源、k6 运行错误 | 看具体错误与 Agent 日志，确认版本后重试 |
| 校准有效但可用容量为 0 | 软上限为 0、全部容量被占用、节点被停用 | 核对三类上限、当前占用和调度级别 |
| 校准过期或配置变化后失效 | 超过 7 天，或 Agent/k6/硬件变化 | 重新校准，不复用旧结论 |
| 节点在线但任务不选择它 | 备用节点未获允许、节点组/指定节点不匹配 | 核对任务节点策略和调度级别 |

## 6. 四种负载模型怎么选

| 页面名称 | k6 模型 | 适合回答 | 新手建议 |
| --- | --- | --- | --- |
| 固定并发 | constant-vus | 固定数量用户持续操作时表现如何 | 适合稳定性与用户并发；无法提前精确知道总迭代数 |
| 阶梯并发 | ramping-vus | 并发逐步增加时从哪里开始退化 | 每级保持足够时间，观察吞吐是否继续增长 |
| 固定吞吐 | constant-arrival-rate | 能否稳定完成指定次数/秒的完整链路 | 第一次最容易理解；建议从 1 次/秒开始 |
| 阶梯吞吐 | ramping-arrival-rate | 吞吐上限和首个明显拐点在哪里 | 已有安全基准后再用，设置停止条件 |

固定并发的实际总迭代数取决于链路耗时，因此页面不应把“VU × 秒”当成准确结果。固定/阶梯吞吐需要足够的 VU 才能按计划启动链路；预检会根据一次真实链路耗时估算所需 VU。

## 7. 场景设计：先保证链路正确，再增加负载

- 选择具有业务代表性的核心链路，而不是随机挑大量接口。
- 每个关键响应同时校验 HTTP 状态和业务字段；HTTP 200 不代表业务成功。
- 需要动态 ID 或令牌时，用前置步骤获取并提取变量，避免写死过期数据。
- 写操作必须设计唯一数据、幂等策略和 cleanup_once 清理；删除/取消要验证终态。
- 数据集按用途选择：cycle 可循环复用；fixed_per_vu 为每个 VU 固定一行；exclusive_per_iteration 每轮独占一行，数据不足应停止而不是串用。
- 保存后形成不可变版本。修改场景时新建版本，报告才可追溯。

> **要点：** 不建议默认压测真实打印、支付、短信、解绑、批量删除、高成本 AI 或不可逆写操作。若确需覆盖，必须使用隔离环境、专用账号/设备、明确的限额和可验证清理。

## 8. 第一次安全跑一遍

### 建议参数

| 项目 | 建议值 | 原因 |
| --- | --- | --- |
| 目标接口 | 只读、低成本、可重复的查询接口 | 避免业务副作用 |
| 环境 | 优先隔离压测环境；生产环境仅在明确授权后使用 | 降低影响真实用户的风险 |
| 负载模型 | 固定吞吐 | 目标清晰，便于理解 |
| 目标 | 1 次完整链路/秒 | 只验证端到端能力与报告链路 |
| 持续时间 | 10 秒 | 最小安全演练 |
| 节点 | 专用首选节点；先不允许备用节点 | 避免主平台所在机器承压 |
| 任务优先级 | 低 | 不抢占更重要的等待任务 |
| 初始阈值 | P95 ≤ 1000 ms；HTTP 错误率 < 1%；业务失败率 = 0 | 先建立可解释的基准，后续按业务 SLO 调整 |

### 操作步骤

1. 打开“压测节点”，刷新并确认专用节点心跳正常、校准有效、容量大于 0。
2. 打开“性能场景”，创建只读场景，补充 HTTP 与业务断言，保存版本。
3. 打开“压测执行”，创建草稿并选择刚保存的场景版本和目标环境。
4. 选择固定吞吐 1 次/秒、10 秒、低优先级、专用首选节点。
5. 执行连通性检查：确认 DNS、TCP/TLS 和基础网络可达。
6. 执行预检：平台以 1 VU 跑一次完整链路，确认变量、断言、数据和清理。
7. 确认预估容量足够后启动。运行中观察目标吞吐、P95、错误、丢弃和节点资源。
8. 进入性能报告，按本说明第 10 节的顺序读报告；最后查看 AI 建议。
9. 若为临时演练，保留报告证据后归档临时场景或运行，不删除历史正式结果。

## 9. 常用专有名词和指标

| 指标 | 它说明什么 | 出现异常时先看什么 |
| --- | --- | --- |
| P50 | 一半请求不超过该耗时，代表典型体验 | 与 P95/P99 的差距 |
| P90/P95 | 90%/95% 请求不超过该耗时，常用于服务目标 | 随负载的趋势和首次突增时间 |
| P99 / Max | 尾部慢请求与极端值 | 慢步骤、超时、GC、锁或外部依赖 |
| Throughput / RPS | 实际每秒 HTTP 请求数 | 是否随目标负载增长 |
| Iteration rate | 实际每秒完成或启动的完整业务链路数 | 是否达到设定到达率 |
| HTTP error rate | 非预期 HTTP 状态或传输失败比例 | 状态码、网络错误、超时分类 |
| Business failure rate | HTTP 成功但业务断言失败的比例 | 业务码、布尔值和关键领域字段 |
| Workflow failure rate | 整条链路失败比例 | 失败发生在哪个步骤 |
| Dropped iterations | 计划启动但因 VU/发压能力不足而没启动的链路 | 预分配 VU、Agent 容量与链路耗时 |
| Threshold | 运行前定义的通过标准 | 必选阈值是否通过，而非只看平均值 |
| Ramp-up | 逐步增加负载的阶段 | 哪个阶段开始延迟或错误突变 |
| Saturation | 资源或队列接近上限 | 目标服务与 Agent 的 CPU、内存、连接池、队列 |
| Evidence completeness | 所有分片与时间窗口是否都有完整证据 | 节点中断、缺失窗口、未完成分片 |

## 10. 报告应该按什么顺序看

1. 先看“负载目标是否达到”。目标没达到时，低延迟可能只是因为实际压力不足。
2. 再看“证据完整性”。节点或时间窗口缺失时，结论只能标为证据不足。
3. 区分 HTTP 错误、网络错误、业务失败和整链路失败，避免把 HTTP 200 当成功。
4. 看 P50、P95、P99 和最大值的分布与趋势，不能只看平均响应时间。
5. 看 dropped_iterations。到达率未达标且丢弃上升时，先判断是 Agent 容量不足还是目标服务变慢导致所需 VU 增加。
6. 对齐 Agent CPU/内存峰值与异常时间。如果 Agent 先饱和，本轮不能证明目标服务容量上限。
7. 检查必选阈值，形成明确通过/不通过结论。
8. 只与同场景版本、兼容环境和相同负载模型的历史运行比较。
9. 最后读 AI 诊断，核对它引用的证据是否真的支持结论。

## 11. AI 能否给出合理建议

AI 可以基于平台已经计算好的确定性证据做归纳和下一轮建议。它的输入包含目标达成率、延迟、错误、丢弃、慢步骤、Agent 资源、时间窗口和可比历史，不包含 Authorization、Cookie、密码或完整敏感响应。

| AI 输出 | 应有内容 | 使用方式 |
| --- | --- | --- |
| 主要结论 | 是否达标，以及最关键的限制因素 | 先与确定性报告核对 |
| 瓶颈分类 | 目标服务、网络、压测节点、测试数据、混合或证据不足 | 分类不是最终根因，只是排查方向 |
| 证据引用 | 指向具体阈值、时间窗口、步骤或节点 | 没有证据引用的结论不应采纳 |
| 改进建议 | 优先级、动作、如何验证 | 优先执行可回滚、可验证的动作 |
| 下一轮建议 | 模型、目标、时长和节点建议 | 作为草案，仍需人确认业务风险 |
| 置信度 | 高/中/低及原因 | 低置信度时先补监控或重跑 |

平台不允许 AI 在诊断结论中重新抄写数值。目标速率、P95、失败率等数字以确定性报告为准；AI 只做定性归纳，并在建议中给出下一轮目标。若模型引用不存在的证据，或在结论里复述无法校验的数字，平台会拒绝该结论，自动降级为低置信度的安全建议，不影响已经固化的确定性报告。

> **要点：** AI 不能仅凭客户端压测指标证明“数据库某条 SQL 慢”或“某段代码有锁”。如果缺少服务端 CPU、GC、连接池、数据库慢查询和链路追踪，合理结论应是“目标服务疑似饱和，证据不足以定位内部根因”，并建议补采证据。

### 判断 AI 建议是否合理的四个问题

- 它是否引用了报告里真实存在的证据编号或指标？
- 它是否区分目标服务、网络、Agent 和测试数据问题？
- 建议是否包含“怎么验证”，而不是只说扩容或优化？
- 下一轮目标是否循序增加，并且没有越过节点容量与生产风险边界？

## 12. 常见问题怎么判断

| 现象 | 判断重点 | 建议动作 |
| --- | --- | --- |
| 目标吞吐未达到，丢弃迭代上升 | Agent VU/速率是否到上限，链路耗时是否拉长 | 先增加预分配 VU或专用节点；若 Agent 不饱和，再查目标服务 |
| P95 上升但错误率仍为 0 | 吞吐是否继续增长，P99/最大值是否同步恶化 | 缩小阶梯，找首次拐点并补服务端监控 |
| HTTP 200 但业务失败 | 业务码、布尔值、领域字段和数据前置 | 修复业务或断言/数据，不得算作通过 |
| Agent CPU/内存先到高位 | 异常时间是否与节点资源峰值一致 | 降低单节点分片或增加同级专用节点后复测 |
| 网络错误集中在一个节点 | 出口 IP、DNS、TLS、跨地域网络 | 从该节点单独做连通性与预检，不直接归因目标服务 |
| 证据不完整或分片中断 | 缺失窗口、节点离线、停止原因 | 本轮标记证据不足，修复节点后按同配置重跑 |
| AI 置信度低 | 缺少哪类证据 | 补日志、APM、数据库或主机指标后重新诊断；重新诊断不会重跑 |

## 13. 多节点和调度级别

| 级别 | 中文含义 | 参与规则 |
| --- | --- | --- |
| 首选节点 preferred | 专用压测服务器 | 自动调度优先使用 |
| 普通节点 normal | 资源稳定、压测期间没有其他重任务的服务器 | 首选容量不足时使用；资源充足的本机也可选择 |
| 备用节点 fallback | 需要优先保护平台服务的本机或应急节点 | 只有任务明确允许时参与 |
| 停用节点 disabled | 保留记录但不再接任务 | 不可调度 |

任务中的目标值是全局总目标。多节点只负责分片，总 VU 或总到达率不会因为节点数增加而自动翻倍。例如目标 100 次/秒、两台同级节点各分 50 次/秒时，总目标仍是 100 次/秒。新增服务器需要独立注册和部署一次 Agent；以后调度级别、节点组、软上限和任务选择都在平台修改。

第一版某节点中途离线时不会把剩余压力自动迁移到其他节点，避免目标服务突然受到额外压力。报告会标记分片未完成和证据不完整。

## 14. 安全边界与生产环境

- 生产环境必须保留 api.production 权限和明确风险确认；没有授权时只查看。
- 当前平台仍通过 HTTP 提供服务，传输风险尚未解决。Agent 到平台和浏览器到平台都应尽快迁移 HTTPS。
- 敏感凭据只放环境密钥或专用机密存储，不写入普通数据集、场景名称或日志。
- 压测账号、数据和设备与真实用户隔离；写操作准备精确清理和数量上限。
- 设置停止条件：错误率突增、P95 超阈值、生产告警、Agent 资源饱和或出现未知副作用时立即停止。
- 飞书通知写清场景、环境、负载目标、结果和报告入口，避免把普通 API 回归与性能报告混淆。

## 15. 推荐的渐进测试计划

| 阶段 | 建议负载 | 目的 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 连通演练 | 1 次/秒 × 10 秒 | 验证节点、场景、预检、报告和 AI 链路 | 业务断言全过、无副作用、证据完整 |
| 小流量基准 | 5 次/秒 × 2 分钟 | 建立响应时间和资源基线 | 目标达到且必选阈值通过 |
| 阶梯探测 | 5→10→20→…，每级 2–5 分钟 | 寻找首个退化阶段 | 每次只增加一个变量，保存拐点证据 |
| 稳定性 | 已知安全容量的 60%–70%，30–60 分钟 | 发现累积性问题 | 资源和延迟无持续漂移 |
| 压力/容量上限 | 隔离环境中逐步越过目标峰值 | 确定极限和保护策略 | 已准备监控、停止条件和恢复方案 |

> **要点：** 服务器内存扩容不会自动等于更高压测能力。扩容、CPU 配额、Agent 镜像或 k6 版本变化后都要重新校准；正式容量仍需用业务压测验证。

## 16. 运行前、运行中、运行后检查清单

### 运行前

- [ ] 场景版本、环境版本和接口归属正确。
- [ ] HTTP 与业务断言完整，动态变量可提取。
- [ ] 写操作有唯一数据、清理和终态验证。
- [ ] 选中节点心跳正常、校准有效、容量充足。
- [ ] 生产环境权限、通知范围和停止条件明确。
- [ ] 连通性检查和单链路预检通过。

### 运行中

- [ ] 实际负载接近目标，未出现持续丢弃迭代。
- [ ] P95/P99、HTTP/业务错误和慢步骤没有异常突变。
- [ ] Agent 与目标服务资源没有先行饱和。
- [ ] 发现真实副作用或生产告警时立即停止。

### 运行后

- [ ] 所有分片都有终态，证据完整性可接受。
- [ ] 报告区分了 HTTP、网络、业务和链路失败。
- [ ] 阈值结论、慢步骤、拐点和资源峰值已记录。
- [ ] AI 结论引用了证据，建议包含验证方法。
- [ ] 临时数据已精确清理，正式报告和运行 ID 已保留。

## 17. 当前版本说明

压测 Agent 0.1.2 在 0.1.1 的 k6 0.52 摘要兼容、非 UTF-8 控制台容错和链路状态传递基础上，改为读取 Docker cgroup CPU 配额。页面“本机硬上限”的 CPU 核数现在反映容器实际可用额度，修改 CPU、内存、VU 或吞吐硬上限后必须重新校准。2026-09-03 已使用本机节点完成一次公开只读接口的最小闭环：固定吞吐 1 次/秒、1 VU、10 秒，共执行 10 次请求和 10 次完整链路，HTTP、业务和链路失败均为 0，P95 为 10 ms，节点正常退出且证据完整。该结果只证明平台与 Agent 的小流量链路可用，不能推导 3D 服务的正式容量。

报告吞吐按配置的施压窗口计算，不把排队、节点就绪和收尾时间混入分母；同一 5 秒内的步骤指标与链路指标合并为一个时间点。历史运行会用当前报告规则重新计算，不会被旧版保存的“证据不足”永久锁住。节点明细默认展示分配压力、调度级别、进程结果和指标窗口，原始 JSON 仅在“查看技术明细”中展开。
