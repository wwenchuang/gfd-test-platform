# 可配置测试应用设计

## 目标

应用与业务线统一由平台“应用配置”维护。UI 自动化和 API 测试在创建、编辑、执行、历史记录、基线与通知中保存并展示同一套应用和业务归属，不再把“智小白3D”写死为所有同事的应用。

## 配置模型

- 应用使用包名 `package` 作为稳定标识，中文 `name` 作为展示名称。
- 每个应用独立维护 `business_lines`，业务线使用隐藏稳定 ID 和中文展示名称。
- 应用支持启用和停用。停用应用不出现在新建入口，但历史记录仍可解析和展示。
- 新建应用必须填写中文应用名、包名，并至少配置一个启用的中文业务线。
- `com.kfb.model`、`home`、`shared` 仅用于兼容历史数据，不能覆盖平台已保存的应用名称和业务线配置。

## 创建与编辑

- UI 自动化新建入口先选择已启用应用，再展示该应用启用的业务线；两者都必选。
- 模块已绑定应用时自动选中并解释来源，但用户可以切换到其他已配置应用。
- 包名作为所选应用的只读信息展示，不再鼓励手工输入未配置包名。
- API 用例编辑器同样先选择应用，再选择该应用业务线。
- 切换应用时，若原业务线不属于新应用则清空业务线并提示重新选择，不能静默改成第一项。
- AI 生成、基础用例生成、复制和新版本保存继承应用与业务；单条编辑允许纠正。

## 持久化与历史兼容

- 用例版本保存 `app_package`、`app_name` 和 `business`。包名用于关联，名称作为历史快照。
- UI YAML 用例继续通过模块、YAML 包名和任务元数据解析应用，单条业务校验必须使用该应用的业务线配置。
- 旧记录有包名时按包名匹配当前配置；只有历史名称时尝试精确匹配配置名称或别名。
- 无法可靠匹配的旧记录显示“未标注应用”，查看不受阻；再次保存或执行前要求补选。
- 删除应用前提示历史影响；常规下线使用“停用”，不删除历史显示所需配置。

## 执行与通知

- UI 和 API 执行快照携带每条用例的应用包名、应用名称和业务线。
- 单应用执行卡片显示该应用；混合应用执行显示去重后的中文应用名列表。
- 业务线按应用分别解析。混合执行时展示去重后的中文业务线，不使用其他应用的同名或默认业务线替换。
- 通知中的“UI 自动化”和“API 测试”保持独立类型，应用和业务均来自执行快照或平台配置。

## 交互与错误处理

- 没有启用应用时，新建入口明确引导到“应用配置”，提交按钮不可用。
- 所选应用没有启用业务线时，明确提示维护业务线，不能回退为“家用/共享”。
- 历史应用或业务已停用时展示历史值和状态，并要求用户在再次保存前重新选择。
- 应用配置列表直接展示状态、业务线、模块、Sonic 和飞书归属，便于检查上下游是否完整。

## 验证范围

- 后端：应用规范化、按应用解析业务线、UI 用例更新、API 用例契约/版本/执行快照、通知聚合。
- 前端：应用配置、新建 UI 用例、API 用例编辑器、列表/基线/任务/报告展示。
- 回归：后端与前端静态检查、API 测试门禁、Vue 测试与构建、主平台与 API 工作台 Chromium 流程。
- 部署后：按“配置应用 -> 新建用例 -> 保存 -> 执行记录 -> 基线 -> 通知预览/卡片”检查上下游衔接；不实际触发 Runner、Sonic 或飞书外发，除非另行明确要求。
