# API 基线断言复核设计

## 目标

对当前约 240 条可重复 API 基线按真实响应重新检查断言，避免只校验 HTTP 200 时把 `code=1001` 等业务失败当成通过。复核必须保留历史版本、执行证据和清理边界，不能批量把所有接口写成 `code=0`。

## 判定规则

- 实际 HTTP 为 4xx/5xx：只有已有状态断言精确匹配该负向预期时才算有效；否则单独标记“实际 HTTP 失败”，不能由结构断言或其他领域断言掩盖。
- 实际响应有 `code`：现有断言必须用“等于”或单值“属于集合”精确匹配实际预期，比较遵循 JSON 类型语义，布尔 `false` 不得与数值 `0` 视为相等。正向成功只接受实际 `0` 或 `200`；实际为其他值且没有同值精确断言时标记“实际业务失败”，不自动把失败码改成预期。
- 实际响应有 `success`：使用精确布尔断言；正向成功为 `true`。
- 没有统一业务字段：保留 HTTP、响应结构或领域字段断言；若只有 HTTP 状态，标记“缺少领域断言”。
- 缺少可解析执行证据：标记“证据不足”，必须重新执行后判断。
- 已有精确负向断言：如果实际失败码与用例明确预期一致，可继续作为负向基线，不强制改成成功码。

## 安全执行

- `GET / HEAD / OPTIONS` 且不依赖动态资源的读取类优先批量复核。
- 资源详情必须由前置步骤动态获取有效 ID。
- 新增、修改、收藏、设备控制、切片和异步任务即使已有步骤也先进入人工复核；平台不能仅凭“步骤存在”证明资源关系和清理语义正确。
- 删除接口只能删除本轮前置创建的临时资源。
- 下发打印只有同时具备启用的资源准备、从主体响应提取本次打印任务标识、以及引用该标识的取消打印清理时才进入受控复核；取消失败则本条执行失败且不得采纳基线。
- 登录、验证码、不可逆业务和无法确定上下游关系的接口只进入人工复核，不自动执行。
- 安全候选必须与当前选择的执行环境等于原基线环境；切换环境后既重新计算候选，也在保存任务和立即执行前再次校验已选审计证据环境，不能沿用旧环境选择。
- 一次性用例只按明确的“一次性 / one-time / one time”标记识别。历史用例可移动到包含“一次性”的持久化分组补标；普通 `API Test` 分组不能作为一次性依据。

## 版本流转

1. 读取当前基线用例、现有断言和采纳时的实际响应证据。
2. 生成只读断言审计，不修改基线。
3. 对可安全复核项创建新用例版本并补精确断言。
4. 使用原基线环境执行新版本。
5. 调试通过后采纳新版本；原活动基线进入 `superseded` 历史。
6. 调试失败、业务失败、清理失败或证据不足的条目保留旧证据并进入人工处理清单，不冒充完成。

## 页面体验

基线页提供“检查断言”，展示总数及各状态数量；列表逐条展示实际 HTTP/业务值、断言结论、执行安全级别和下一步原因。用户可筛选并选择“可安全复核”项，进入既有基线执行和编辑流程，不新增隐式批量写入。审计只查询当前活动基线，最近 AI 生成任务及其接口版本匹配也由 PostgreSQL 限量筛选，避免历史数据增长后在应用层全量扫描。
