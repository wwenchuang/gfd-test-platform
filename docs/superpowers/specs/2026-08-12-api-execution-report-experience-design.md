# API 执行明细与测试报告体验设计

## 1. 背景

平台已经保存 API 执行、逐用例结果、请求响应、断言、执行轨迹、失败分析，并通过 SSE 推送实时事件。当前页面的问题不是缺少数据，而是信息组织过于单调：执行记录主要呈现原始事件，报告列表主要呈现统计数字，用户需要多次展开和阅读 JSON 才能确认执行过程、失败性质和处理方向。

本设计在现有 API 测试架构内收敛展示方式，不新增平行执行系统或报告数据源。用户已确认：

- 执行页采用“结构化执行控制台”。
- 报告页采用“诊断型测试报告”。

## 2. 目标

1. 实时执行时，一屏看清当前进度、逐用例状态、接口耗时和最新失败。
2. 执行完成后，一屏回答本次是否通过、失败属于什么类别、应优先处理什么。
3. 请求、响应、断言、执行轨迹和 AI 分析可追溯，但不让原始 JSON 淹没主视图。
4. 已通过、失败、运行异常、跳过和取消保持真实统计，父执行失败不能覆盖已经通过的子用例。
5. 敏感变量和请求头始终使用现有脱敏结果，不在日志或报告中恢复原值。
6. 桌面端适合持续观察，移动端仍可查看状态、失败结论和关键证据。

## 3. 非目标

- 不改变执行状态机、断言语义、失败分类和基线门禁。
- 不新增数据库表、迁移、执行模式或报告生成服务。
- 不把 AI 结论作为最终状态来源，AI 只能解释已有确定性结果。
- 不重构 `task_server/router.py`，不影响 UI Agent、Midscene、Runner 或 Sonic。
- 不在本轮增加趋势图、跨版本质量评分、定时报告、邮件通知或 PDF 导出。
- 不复制参考产品的整页黑色终端视觉；技术日志只是证据视图，不是唯一阅读方式。

## 4. 数据边界

所有展示复用现有数据：

- `ExecutionView`：任务类型、环境、状态、开始和结束时间、汇总、逐用例结果。
- `ExecutionEventView`：SSE 实时事件、事件级别、用例关联和安全载荷。
- `ExecutionCaseResult`：用例名称、接口方法和路径、状态、耗时、请求、响应、断言、轨迹和失败分析。
- 现有执行详情接口：SSE 断开或终态时刷新最终快照。

前端可以派生通过率、总耗时、当前进度和失败类别数量，但不能自行改写后端状态。若实时事件缺失可选显示字段，界面使用已有用例结果补充名称和接口；不得猜测业务结论。

## 5. 结构化执行控制台

### 5.1 页面结构

执行页保留左侧执行历史，右侧主区域改为三层：

1. **任务摘要栏**
   - 任务名称和执行 ID。
   - 执行环境名称及版本。
   - 当前状态。
   - 总数、通过、失败、运行异常、跳过和总耗时。
   - 运行中提供取消；终态失败提供重跑失败项。

2. **视图标签**
   - `实时轨迹`：执行时默认。
   - `用例明细`：终态后可以默认记住用户上次选择。
   - `测试报告`：展示与报告页一致的诊断摘要，并提供进入完整报告的入口。

3. **实时轨迹工作区**
   - 左侧为本次逐用例列表。
   - 右侧为结构化实时日志。
   - 点击用例后，在当前页展开或打开现有详情抽屉查看完整证据。

### 5.2 逐用例列表

每行固定展示：

- `PASSED`、`FAILED`、`BROKEN`、`SKIPPED`、`CANCELLED` 或运行状态。
- 用例名称。
- HTTP 方法和接口路径。
- 耗时；未执行时展示等待或跳过原因。

列表支持按状态筛选。失败项置顶仅作为显式筛选，不自动改变原始执行顺序。选中行使用边线和浅色背景，不使用大面积高饱和色。

### 5.3 结构化实时日志

日志每行展示：

- 时间。
- 级别：信息、执行、通过、失败、跳过、AI 分析。
- 用例名称或任务阶段。
- 接口、HTTP 状态、业务断言结果和耗时等核心摘要。

请求响应的完整 JSON 默认不展开。事件有安全载荷时提供“查看详情”，使用键值或格式化 JSON 展示。日志工具包括：

- 级别筛选。
- 用例筛选。
- 自动跟随开关。
- 用户向上滚动时暂停自动跟随，明确显示“有新日志”，由用户恢复。
- SSE 断开时显示连接状态和重新连接按钮；已有日志不清空。

终态事件追加真实汇总，例如“5 通过 / 1 失败 / 1 跳过”，但汇总值来自最终执行快照，不根据可见日志行计数。

### 5.4 详细证据

点击用例后展示：

- 用例结论和失败类别。
- 脱敏请求摘要与完整请求。
- 脱敏响应摘要与完整响应。
- 每条断言的期望值、实际值和通过状态。
- 变量提取及依赖轨迹。
- AI 失败分析、依据和建议。
- 编辑用例、仅重跑失败项等已有操作。

`FAILED` 表示产品断言未满足；`BROKEN` 表示脚本、数据、环境或平台问题；`SKIPPED` 必须展示上游依赖或取消原因。

## 6. 诊断型测试报告

### 6.1 报告首页

报告列表不再把五个统计格重复铺满每一行。每条记录紧凑展示：

- 任务名称、执行类型和时间。
- 环境名称及版本。
- 最终结论。
- 通过率和通过、失败、异常、跳过数量。
- 总耗时。

点击记录进入完整报告，不再只打开由原始 JSON 组成的抽屉。

### 6.2 完整报告结构

完整报告按下列顺序组织：

1. **报告标题与结论**
   - 任务、执行 ID、环境版本、执行时间和类型。
   - 明确显示“通过”“未通过”“运行异常”“已取消”等结论。

2. **关键指标**
   - 总用例、通过、断言失败、运行异常、跳过、通过率和总耗时。
   - 颜色只用于状态区分，不把整个区域做成彩色卡片墙。

3. **AI 结论与处理建议**
   - 汇总已存在的确定性失败类别和逐用例失败分析。
   - 明确指出主要失败集中点、是否存在环境或鉴权问题、建议的下一步。
   - AI 不得把失败改成通过，也不得覆盖平台失败分类。
   - 没有 AI 分析时显示确定性摘要，不显示伪造建议。

4. **失败分类**
   - 产品断言失败。
   - 脚本或测试数据问题。
   - 环境、网络或基础设施异常。
   - 依赖跳过和取消。

5. **用例明细表**
   - 状态、用例、接口、耗时和一句话结论。
   - 支持全部、失败、异常和跳过筛选。
   - 点击某行后在右侧显示该用例证据。

6. **失败证据面板**
   - 请求和响应摘要。
   - 断言的期望与实际。
   - 失败类别和 AI 分析。
   - 查看完整请求、响应和执行日志。
   - 编辑用例和重跑失败项。

### 6.3 技术日志

参考截图中的终端式技术明细作为报告内的可展开视图或复制内容保留。它按执行顺序输出 `PASS`、`FAIL`、`BROKEN` 和 `SKIP`，包含接口、耗时及失败摘要，但不作为报告默认首页。

## 7. 组件边界

优先调整和复用现有组件：

- `ExecutionConsole.vue`：任务摘要、标签和实时执行布局。
- `ExecutionLog.vue`：结构化事件行、筛选、自动跟随和详情展开。
- `CaseResultList.vue`：统一的逐用例状态列表。
- `ExecutionDetailDrawer.vue`：证据详情，替换默认全量 JSON 堆叠。
- `ReportSummary.vue`：可复用的紧凑摘要，不承担完整报告布局。
- `ReportsView.vue`：紧凑历史列表与完整诊断报告。

若单个组件职责过大，可以增加只负责展示的组件，例如 `ExecutionOverview`、`CaseEvidence` 和 `DiagnosticReport`。它们只接收类型化数据和发出操作事件，不自行请求后端。

## 8. 响应式与可访问性

- 桌面端实时视图为用例列表和日志双栏；报告为明细主区和证据侧栏。
- 小屏幕改为单列，摘要先显示，证据位于用例行下方或抽屉中。
- 固定状态列和操作按钮尺寸，动态内容不能造成布局跳动。
- 颜色之外同时显示状态文字或图标。
- 日志、标签和详情控件支持键盘操作，抽屉保留焦点管理和 Esc 关闭。
- 长路径和长失败原因允许换行或省略后查看完整内容，不覆盖相邻控件。

## 9. 错误与降级

- SSE 断开：保留已接收日志，显示断开时间和重连按钮，并继续轮询最终执行快照。
- 事件载荷不完整：展示事件类型和已有信息，不拼接未确认的字段。
- AI 分析待生成：显示“分析中”，终态后按现有轮询刷新；分析失败时保留确定性失败原因。
- 请求响应过大：默认展示摘要，完整内容在展开区内滚动，不撑开整页。
- 无报告：显示清晰空状态和返回工作台入口。
- 敏感字段：只消费后端脱敏字段；前端再次对常见授权键名做显示保护，复制技术日志也不能泄露原值。

## 10. 验收标准

### 10.1 执行页

- 运行中可实时看到每条用例的状态变化和结构化事件。
- 自动跟随在用户主动向上浏览时不会强制跳回底部。
- SSE 断开可重连，旧日志和当前选择不丢失。
- 终态统计与后端执行快照一致。
- `FAILED`、`BROKEN` 和 `SKIPPED` 的文案和颜色明确区分。
- 请求、响应、断言、依赖轨迹和 AI 分析可从用例进入查看。

### 10.2 报告页

- 报告列表可快速比较结论、环境、通过率和耗时。
- 完整报告一屏包含结论、指标、失败分类、AI 摘要和用例明细。
- 失败行可直接查看期望值、实际值、请求响应和处理建议。
- 已通过用例不会因父执行失败而被显示为失败。
- 没有 AI 结果时仍能依据确定性数据完整阅读报告。

### 10.3 验证范围

- 组件测试覆盖状态映射、筛选、自动跟随暂停、事件展开和报告分类。
- Store 测试覆盖 SSE 断线重连、终态刷新和旧执行切换。
- Chromium 端到端测试覆盖运行中的日志变化、失败明细、报告打开和失败重跑入口。
- 桌面与移动截图检查无重叠、溢出和空白主区域。
- API 测试完整门禁、前端静态检查、生产构建和 `git diff --check` 通过。

## 11. 实施顺序

1. 先抽取统一状态文案、摘要和证据展示组件，并补组件测试。
2. 改造结构化执行控制台和实时日志交互。
3. 改造报告历史列表和诊断型完整报告。
4. 补 SSE 降级、移动端和端到端验收。
5. 完整回归 API 测试门禁后更新 `CODEX_STATE.md` 并直接提交到 `main`。
