# 云真机操作录制与 YAML 生成设计

## 目标

用户从测试平台发起录制后，在 Sonic 原生远程控制页面操作 Android 手机。平台旁路记录操作、关键证据和页面结构，将它们转成可编辑、可校验、可单条调试的 Midscene YAML 草稿。

## 范围

第一版支持启动应用、单击、文本输入、Android 返回键、上下滑动和人工检查点。Sonic 保持原生实时画面与触控；测试平台显示录制状态和步骤时间线，允许删除、修改和合并步骤。结束后生成 YAML 草稿，但不自动覆盖已验证基线。

第一版不支持多指手势、验证码自动处理、系统权限修改、跨应用文件选择器自动语义化或直接采纳为基线。

## 架构

Sonic 继续负责设备登记、占用状态、实时视频和触控执行，测试平台负责录制会话、操作证据、YAML 草稿和安全门禁。Sonic 2.7.2 的实时画面使用独立的 screen WebSocket，点击、滑动、输入和按键使用控制 WebSocket；录制钩子只镜像已经发送成功的控制动作，不代理、不延迟也不重发原控制消息。

测试平台打开 Sonic 原生远程页面时附带一次性录制会话标识。部署在 Sonic Web 客户端中的小型录制钩子把归一化动作异步提交到平台；提交失败只在录制时间线标红，不阻塞当前触控。Windows Runner 在动作稳定后按需采集 `uiautomator dump` XML 和关键帧，禁止按视频帧连续截图。

这种方式保持 Sonic 原有 scrcpy 视频链路和触控手感。测试平台不再实现一套低帧率远程控制页面，也不把手机画面经过平台服务转发。

## 设备与会话约束

- 生产真机只允许 `9888E0094F2A`，不允许 `18CEDF5BA7B2` 或自动回退其他设备。
- 设备必须同时在 Runner 和 Sonic 中可用；任一来源忙碌或不可确认时禁止开始。
- 一台设备同时只有一个录制会话。会话记录发起人、Runner、设备、应用、起止时间和终态。
- 页面关闭、心跳超时或 Runner 离线后会话进入可恢复的暂停态；只有发起人或管理员可继续或结束。
- 所有设备命令都必须带服务端生成的会话 ID、递增序号和短期命令 ID，Runner 拒绝重放与跨设备命令。

## 证据与操作语义

每个步骤保存原始动作、开始/结束时间、关键截图、动作后的 XML、命中控件的 text/resource-id/content-desc/class/bounds 和采集结果。首次动作补录操作前证据；连续动作采用上一动作的结果作为下一动作的前态，避免重复截图。坐标只是录制证据，不默认写入最终 YAML。

点击优先用命中控件的可见文字生成 `aiTap`，其次使用 content-desc 和 resource-id 辅助生成可读描述；信息不足时结合截图由 AI 生成候选，仍不确定时标记“需要确认”。滑动转为官方 `aiScroll`；输入转为 `aiTap` + `aiInput/value`；检查点只能转为 `aiWaitFor` 或 `aiAssert`。

## YAML 生成与门禁

生成结果必须包含应用 `launch`、可读的任务名和 flow。只允许现有生产 Midscene action，并经过 YAML 静态校验、可执行性评分和现有修复规则。AI 只能在录制证据与 Top3 相似成功基线范围内改写描述，不能新增未操作的副作用步骤。

草稿默认保存到测试库。单条调试通过不等于自动采纳基线；需用户明确点击采纳并继续遵守平台冒烟门禁。

## 前端交互

在“用例”下新增“云真机录制”。开始前选择应用，设备固定为指定测试设备；平台创建会话并打开 Sonic 原生远程页面。平台页保留步骤时间线和“添加检查点”，Sonic 页继续承担实时画面、点击、输入、返回和滑动。每步明确显示“已识别”、“需要确认”、“证据待采集”或“记录失败”。

“结束录制”后先显示 YAML 预览、静态校验和可执行性评分，再允许保存或单条调试。任何未确认步骤都阻止直接调试。

## 验收

1. 非指定设备、设备忙碌、Runner 离线或 Sonic 状态不可确认时无法开始。
2. 点击、输入、返回、滑动各完成一次，Sonic 操作手感和未录制时一致，动作证据和控件元数据可查。
3. 断线后会话可恢复，不重复执行已完成命令。
4. 坐标不直接进入 YAML，无可靠语义的步骤被标记需要确认。
5. 生成的 YAML 通过 action 白名单和静态校验；未通过时不能创建 Runner 任务。
6. 录制不启用连续截图；结束后停止证据采集并释放录制会话，Sonic 设备占用按其原流程释放。
