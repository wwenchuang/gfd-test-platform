# API 测试 Phase 2 场景编排与生产闭环设计

## 1. 背景

API 测试 Phase 1 已经提供项目和工作区、Apifox 手动刷新、不可变接口与环境版本、AI 用例草稿、结构化用例编辑、单例调试、基线采纳、异步执行、实时日志、报告和持久测试任务。

下一阶段不应再建设一套平行工作流，也不应先做定时任务、Mock 或通知。当前优先级是先让现有生产链路可靠可诊断，再补齐多接口业务场景需要的测试集、依赖编排、变量传递、批量调试、基线回归、失败重跑和契约影响分析。

本设计是 `2026-08-08-api-testing-platform-design.md` 和 `2026-08-10-api-testing-completion-design.md` 的增量规格，保留现有 PostgreSQL、Redis、Celery、Vue 3、SSE、AI Gateway 和 `/api/api-testing/v1` 边界。

## 2. 目标

本阶段完成四个可独立验收的里程碑：

1. **M0：生产稳定性与真实闭环**
   - 部署、依赖、数据库、迁移、Redis、Worker 和 AI Gateway 状态可检查、可定位。
   - 线上真实跑通“我的收藏”三个接口的完整流程。
2. **M1：测试集和依赖编排**
   - 用不可变测试集版本表达顺序、并行、条件、变量提取与显式传递。
   - 执行前拒绝循环、缺失变量、跨范围引用和不可执行用例。
3. **M2：批量调试、基线回归与失败重跑**
   - 批量调试不修改基线。
   - 只有已通过的精确用例版本才能采纳为基线。
   - 失败重跑保留原始结果并创建可追溯的新执行。
4. **M3：契约影响分析、版本审计与完整验收**
   - 手动刷新接口后，在激活新版本前展示受影响用例、测试集和基线。
   - 用户可以比较版本并追踪关键变更历史。

最终主链保持不变：

```text
选择接口
→ AI 生成或补全测试设计
→ 人工按需调整测试数据
→ 单例或批量调试
→ 采纳基线 / 组成测试集
→ 执行
→ 实时日志与报告
→ AI 辅助分析失败
```

## 3. 非目标

以下能力明确留给后续阶段：

- 定时任务、Cron 编排和发布流水线触发。
- 多 Worker 租约、跨节点分片和分布式调度。
- 邮件、企业微信、飞书或 Webhook 通知。
- Mock 服务、Mock 规则和虚拟数据服务器。
- 性能测试、安全扫描和流量回放。
- 完整 RBAC、组织级配额和多租户计费。
- 自动后台刷新 Apifox。
- 任意 Python、JavaScript 或 Shell 脚本执行。
- 重构 `task_server/router.py` 或改变 UI Agent、Midscene、Runner、Sonic 主链。

## 4. 核心原则

### 4.1 复用 Phase 1，不新建平行系统

测试集引用现有 `ApiCaseVersion`，执行复用现有 `ApiExecution`、`ApiExecutionCase`、`ApiExecutionAttempt`、事件流和报告。新增服务通过现有 API 测试模块注册，不把业务逻辑放入 `router.py`。

### 4.2 三层资产保持分离

1. **接口源数据**：来自 Apifox/OpenAPI 的不可变版本。
2. **测试资产**：用例版本、基线、测试集版本、依赖和变量映射。
3. **执行实例**：提交时解析出的不可变运行快照、请求、响应、日志和结果。

源版本更新不能静默修改测试资产；测试资产更新不能改写历史执行。

### 4.3 AI 参与设计，平台执行确定性门禁

AI 可以：

- 分析接口契约和业务风险。
- 生成正向、异常、边界、鉴权和依赖用例草稿。
- 建议变量提取、断言和测试集关系。
- 总结契约变化影响和执行失败。

平台必须：

- 校验 JSON 合同、变量作用域、DAG、执行限制和安全策略。
- 决定用例是否可执行、是否可以采纳为基线、下游是否跳过。
- 保留原始结果，不允许 AI 把失败改成成功。

### 4.4 状态与统计必须真实

执行状态与失败类别分开：

- 状态：`QUEUED`、`RUNNING`、`PASSED`、`FAILED`、`BROKEN`、`SKIPPED`、`CANCELLED`。
- 类别：产品断言、鉴权、测试数据、脚本定义、环境、网络、超时、契约漂移、取消、未知。

产品断言失败是 `FAILED`；平台、环境、变量解析或脚本定义问题是 `BROKEN`；因上游未成功而未执行是 `SKIPPED`。父执行可以失败，但已通过的子用例仍显示真实通过数。

## 5. M0：生产稳定性与真实闭环

### 5.1 就绪检查

新增 API 测试专用就绪接口：

```text
GET /api/api-testing/v1/readiness
```

返回组件级状态，不返回密码、连接串、密钥或内部堆栈：

- `database.connected`
- `database.migration_revision`
- `database.expected_revision`
- `redis.connected`
- `worker.available`：由 Worker 写入 Redis 的短 TTL 心跳判断，不在每个页面请求中同步执行 Celery ping
- `worker.queue`
- `ai_gateway.available`
- `api_testing.enabled`
- 总体 `ready`

`/api/health` 继续表示 Task Server 进程健康；API 测试 readiness 表示 API 测试子系统可以实际接单。两者不得混为一谈。

### 5.2 部署与迁移

部署流程必须按以下顺序执行并在失败时停止：

1. 校验 `/opt/midscene.env` 必需变量存在。
2. 校验 `API_TESTING_DATABASE_URL` 能连接现有 PostgreSQL。
3. 校验 Redis 可达。
4. 执行 Alembic `upgrade head`。
5. 校验数据库 revision 等于代码 head。
6. 重启 Task Server 和 Worker。
7. 调用 Task health、API readiness 和 AI Gateway health。

Compose 只负责创建容器，不负责在已有数据卷上自动重置数据库角色密码。若 URL 密码与已有角色不一致，部署脚本必须以中文明确报错并给出无损修复指引，禁止继续启动成“进程正常、接口 500”的半可用状态。

数据库、Redis、Worker、AI Gateway 任一关键依赖失败时，前端显示组件级原因和请求编号，不显示泛化的“服务器错误”。

### 5.3 错误可诊断性

API 测试请求生成 `request_id`，错误响应采用统一结构：

```json
{
  "error": {
    "code": "DATABASE_UNAVAILABLE",
    "message": "API 测试数据库暂不可用",
    "request_id": "...",
    "retryable": true
  }
}
```

服务端日志记录请求编号、路由、用户编号、异常类别和内部堆栈。响应不包含密钥、请求 Authorization、数据库密码、完整业务 token 或敏感响应体。

### 5.4 “我的收藏”真实闭环验收

线上使用已保存的生产环境和服务端安全存储的有效业务 token，完成：

1. 选择“我的收藏”三个接口。
2. AI 生成用例草稿。
3. 校验并保存用例版本。
4. 分别调试三个接口。
5. 采纳通过版本为基线。
6. 使用现有持久测试任务执行三个基线，并持续读取 SSE 到终态。
7. 检查请求、响应、断言、提取、日志、截图之外的执行证据和失败类别。
8. 验证页面刷新后任务、执行和报告仍可恢复。

业务接口返回失败可以作为真实结果，但平台不得出现 500、卡死、错误成功、日志无限刷新或密钥泄露。

## 6. M1：测试集和依赖编排

### 6.1 数据模型

#### ApiSuite

可编辑测试集身份：

- `id`
- `project_id`
- `workspace_id`
- `name`
- `description`
- `status`：`DRAFT`、`ACTIVE`、`ARCHIVED`
- `current_version_id`
- 创建人、更新时间

测试集身份可重命名；历史版本不可变。

#### ApiSuiteVersion

不可变测试集快照：

- `id`
- `suite_id`
- `version_number`
- `source_revision_id`
- `environment_revision_id` 可为空，允许执行时选择兼容环境
- `graph_hash`
- `validation_status`
- `created_from`：`MANUAL`、`AI_DRAFT`、`CLONE`
- 创建人、创建时间

一旦用于执行，版本内容不可修改；编辑产生新版本。

#### ApiSuiteNode

图中的执行节点：

- `id`
- `suite_version_id`
- `node_key`：版本内稳定且唯一
- `case_version_id`：必须引用精确 `ApiCaseVersion`
- `display_name`
- `position`
- `timeout_ms` 可在平台限制内覆盖

节点不直接引用可变的 `ApiCase.current_version_id`，避免执行期间漂移。

#### ApiSuiteEdge

节点之间的显式依赖：

- `suite_version_id`
- `upstream_node_key`
- `downstream_node_key`
- `condition`：本阶段仅支持 `SUCCESS`
- `variable_mapping`

`variable_mapping` 必须显式列出：

```json
{
  "favorite_id": "favorite_id",
  "resource_id": "created_resource_id"
}
```

左侧是上游导出名，右侧是下游运行时变量名。禁止隐式把上游所有输出合并到下游。

#### ApiSuiteAuditEvent

记录测试集创建、发布新版本、归档、执行、基线变更和影响确认。只保存操作者、动作、对象、版本、时间和脱敏摘要。

### 6.2 变量作用域

变量按优先级分层：

1. 平台内置只读变量，如执行编号和当前时间。
2. 环境公共变量和服务地址。
3. 环境密钥引用。
4. 执行提交时允许覆盖的非密钥变量。
5. 当前节点显式导入的上游变量。
6. 当前用例数据行变量。

同一层出现同名变量时拒绝执行，不做静默覆盖。密钥只能通过环境密钥引用使用，不能由上游提取写入密钥命名空间。

提取规则只处理允许的响应状态、响应头和受大小限制的 JSON 响应体。提取结果以类型化值保存，日志只显示变量名、类型和脱敏摘要。

### 6.3 DAG 校验

发布测试集版本和提交执行时均执行确定性校验：

- 节点数至少 1，单版本最多 100。
- `node_key` 唯一。
- 节点和边均属于同一测试集版本。
- 引用的用例版本属于同一项目和工作区。
- 用例版本可执行且接口版本仍存在。
- 图中无环。
- 所有上游导出名存在。
- 下游占位符可由允许的变量作用域解析。
- 不允许孤立的未知边、重复边和节点自依赖。
- 不允许跨项目读取环境、密钥、用例或源版本。

校验返回结构化问题列表，包含节点名称、字段、错误码和修复建议，不只返回一段文本。

### 6.4 执行语义

提交时创建不可变执行快照，记录：

- 测试集版本。
- 精确用例版本列表。
- 环境版本和密钥 revision 指纹。
- DAG、变量映射、执行限制和提交人。

Worker 按拓扑层执行：

- 无依赖节点可以并行。
- 默认并发 4，用户可选 1 到 8，服务端强制上限 8。
- 同一节点仅在所有 `SUCCESS` 上游通过并完成变量导出后运行。
- 上游 `FAILED`、`BROKEN` 或 `CANCELLED` 时，下游记为 `SKIPPED`，原因指向阻断节点。
- 用户取消后停止调度新节点；尚未开始且仅因用户取消而未运行的节点记为 `CANCELLED`，因依赖失败未运行的节点仍记为 `SKIPPED`。正在发送的 HTTP 请求按已有取消能力收敛：在取得业务结果前成功中止则记为 `CANCELLED`，已经取得的真实结果保持不变。
- 运行时不重新读取测试集或用例的 current version。

父执行状态按固定优先级聚合：

1. 用户取消且执行尚未自然结束时为 `CANCELLED`。
2. 任一已运行节点为 `FAILED` 时为 `FAILED`。
3. 没有 `FAILED`，但任一已运行节点为 `BROKEN` 时为 `BROKEN`。
4. 所有实际运行节点为 `PASSED` 时为 `PASSED`。

`SKIPPED` 不覆盖上游的真实结果；报告始终分别统计所有子节点状态。已完成节点的结果不会因父执行取消或失败而被改写。

### 6.5 前后处理边界

本阶段只支持声明式处理：

- 设置、删除或复制非密钥变量。
- 基于 JSONPath 从响应中提取值。
- 生成 UUID、时间戳和随机字符串等平台内置值。
- 对字符串做有限的 URL 编码、Base64 和哈希转换。

不执行任意 Python、JavaScript、Shell 或模板表达式。所有操作必须在白名单、参数 schema、输出大小和超时限制内。

## 7. M2：批量调试、基线回归与失败重跑

### 7.1 批量调试

批量调试用于验证草稿，不要求先采纳基线：

- 支持选择多个用例版本或一个测试集草稿。
- 支持本次运行覆盖非密钥环境变量。
- 生成正式执行记录，`mode=DEBUG`。
- 展示逐例请求、响应、断言、提取和日志。
- 不更新 `ApiBaseline`，不修改测试集版本。

批量调试完成后，页面按通过、失败、基础设施异常和跳过分组，用户可以逐条修订或批量采纳符合门禁的版本。

### 7.2 基线采纳门禁

用例版本成为基线必须满足：

- 精确用例版本在所选精确环境版本上至少有一次 `PASSED` 调试。
- 调试使用的源版本、环境版本和用例版本与采纳目标一致。
- 没有未解析变量、跳过断言或密钥缺失。
- 操作者明确点击采纳。

环境或源版本变化后，旧基线仍保留，但显示“需要重新验证”，不会被自动删除或自动升级。

### 7.3 基线回归

回归入口支持：

- 当前测试任务内的全部基线。
- 选中模块的全部基线。
- 指定测试集版本。

提交前显示精确数量、环境、版本和不可执行项。不可执行项不得悄悄丢弃；用户必须看到阻断原因。

### 7.4 失败重跑

失败重跑创建新 `ApiExecution`，不修改原执行：

- `parent_execution_id` 指向原执行。
- `rerun_reason` 为 `FAILED_ONLY`、`BROKEN_ONLY` 或 `SELECTED`。
- 默认只选原执行中的 `FAILED` 和 `BROKEN`，不重跑 `PASSED`。
- 仍使用原执行快照中的用例版本、环境版本和变量输入。
- 若用户选择升级到新版本，必须走“基于原执行创建新任务”，不能标记为原执行重跑。

报告同时显示原执行和重跑执行的真实统计，不用重跑结果覆盖原失败。

## 8. M3：契约影响分析与版本审计

### 8.1 确定性影响分析

Apifox/OpenAPI 手动刷新生成预览后，平台先按确定性规则计算影响：

- 使用 endpoint `stable_key` 匹配接口。
- 比较 method、path、参数必填性、参数类型、请求 schema、响应状态和响应 schema。
- 通过 `ApiCaseVersion.endpoint_id` 找到直接受影响用例。
- 通过 `ApiSuiteNode.case_version_id` 找到受影响测试集版本。
- 通过 `ApiBaseline.case_version_id` 找到需要重新验证的基线。

影响等级：

- `BREAKING`：删除接口、method/path 改变、增加必填参数、收紧类型或删除已断言响应字段。
- `RISKY`：响应或请求结构变化，但不能确定是否破坏当前用例。
- `SAFE`：描述、示例或向后兼容字段变化。

AI 可以用中文总结业务影响和建议，但不能修改影响等级或自动激活新源版本。

### 8.2 版本比较

用户可以比较：

- 两个接口源版本。
- 两个环境版本，密钥只比较指纹是否变化。
- 两个用例版本。
- 两个测试集版本。
- 两次执行结果。

默认展示业务名称和结构化差异，内部 ID 只在技术详情中显示。

### 8.3 审计历史

以下动作写入审计事件：

- 保存或激活源版本。
- 保存环境版本和更新密钥。
- 创建、编辑、验证或采纳用例版本。
- 创建、发布或归档测试集版本。
- 提交、取消或重跑执行。
- 确认契约影响。

审计记录不可由普通业务接口修改，不包含密钥明文和完整敏感请求/响应。

## 9. API 设计

保持 `/api/api-testing/v1` 前缀，新增资源式接口：

```text
GET    /readiness

GET    /suites
POST   /suites
GET    /suites/{suite_id}
POST   /suites/{suite_id}/versions
GET    /suite-versions/{version_id}
POST   /suite-versions/{version_id}/validate
POST   /suite-versions/{version_id}/publish

POST   /executions                     # case versions or suite_version_id
POST   /executions/{execution_id}/rerun
GET    /executions/{execution_id}
GET    /executions/{execution_id}/events

GET    /source-previews/{preview_id}/impacts
POST   /source-previews/{preview_id}/impact-confirmation

GET    /audit-events
```

所有写接口校验当前用户、项目、工作区和对象范围。关键创建接口支持幂等键，避免前端重复点击产生重复测试集版本或执行。

SSE 继续使用短期、单执行、单用户 ticket，不把平台登录 token 放入 URL。

## 10. 前端设计

### 10.1 导航保持收敛

Vue 应用继续只保留：

- 工作台
- 测试资产
- 执行记录
- 测试报告
- 配置

不增加“依赖中心”“批量调试”“影响分析”等一级菜单。

### 10.2 测试集编排入口

工作台在接口选择区增加“保存为测试集 / 加入测试集”。测试资产页在用例列表旁提供测试集列表。

默认编辑器是紧凑有序列表，显示：

- 序号和并行组。
- 用例业务名称、method 和 path。
- 前置依赖。
- 导出变量和导入变量。
- 校验状态。

只有存在分支或多个依赖时才显示图视图。图视图用于理解关系，不替代结构化表单。

### 10.3 调试与执行

单例和批量调试共用现有 Debug Drawer；批量模式增加左侧用例结果列表。执行控制台保持稳定日志区域，只追加增量事件：

- 自动跟随默认开启。
- 用户滚动离开底部后暂停自动跟随。
- 页面轮询不得重置滚动、折叠状态或当前选中用例。
- 终态后停止轮询或 SSE 重连。

### 10.4 报告与影响展示

报告先显示真实统计和阻断链，再显示 AI 总结。失败重跑按钮明确写出重跑数量。

接口更新预览在激活按钮前展示：

- 变化接口数量。
- 受影响用例、测试集和基线数量。
- breaking/risky/safe 分组。
- 查看结构化差异入口。

## 11. 安全与限制

- 数据库密码、Apifox token、业务 token 和环境密钥只存服务端安全配置或加密字段。
- 前端只接收掩码、指纹、是否已配置和更新意图。
- 日志和报告统一脱敏 Authorization、Cookie、token、secret、password 等字段。
- HTTP 执行继续使用现有 host allowlist、DNS 固定、防 SSRF、重定向、响应大小和超时限制。
- 单测试集最多 100 节点、并发最多 8、单次提取值和事件大小设硬上限。
- 请求、响应和 artifact 的保存策略沿用 Phase 1，超限内容截断并记录截断标记。

## 12. 迁移与兼容

新增 Alembic revision，不修改已应用的 `0001` 到 `0003`。

迁移只新增测试集、边、审计、影响关系和执行 lineage 所需表或字段。现有用例、基线、执行和持久测试任务继续可读。

旧的单用例和基线回归接口继续工作；新执行提交在内部统一转换为执行快照。前端在后端 readiness 未通过时禁用 API 测试写操作，但仍允许查看已有资产和历史报告。

## 13. 测试策略

### 13.1 后端单元测试

- DAG 拓扑排序、循环、自依赖、重复边和缺失节点。
- 变量作用域、显式映射、冲突、缺失和密钥隔离。
- 上游失败后的下游 `SKIPPED` 语义。
- 并发层执行、取消和超时。
- 批量调试、基线门禁、失败重跑 lineage。
- 契约 diff 的 breaking/risky/safe 分类和影响映射。
- readiness 在数据库、迁移、Redis、Worker、AI Gateway 各种组合下的结果。

### 13.2 API 集成测试

- 迁移从 `0003` 升级到新 head。
- 测试集 CRUD、不可变版本、发布和范围隔离。
- 测试集执行、SSE、取消、重跑和报告。
- 幂等键避免重复提交。
- 未登录、越权、跨项目和无效引用。
- 错误响应含 request_id 且不泄露敏感信息。

### 13.3 前端测试

- 测试集列表/图切换和结构化编辑。
- 校验错误定位到具体节点。
- 批量调试不触发基线采纳。
- 运行日志增量追加、滚动保持和终态停止。
- 报告真实展示 PASSED/FAILED/BROKEN/SKIPPED。
- 内部 ID 不作为默认环境、接口或测试集名称。
- 桌面与手机视口无重叠、无水平溢出。

### 13.4 生产验收

每个里程碑必须同时通过：

1. 聚焦单元和集成测试。
2. API 测试完整门禁。
3. Python/TypeScript/Vue 构建和 `git diff --check`。
4. 浏览器桌面与手机截图检查。
5. 部署后 Task health、API readiness、AI Gateway health。
6. 真实“我的收藏”三个接口闭环，持续监督到终态。

## 14. 里程碑验收门槛

### M0 完成标准

- PostgreSQL、Redis、Worker、迁移和 AI Gateway 状态可由 readiness 准确反映。
- 数据库密码不一致、迁移落后、Worker 离线时不再只返回模糊 500。
- 生产部署脚本可重复执行，不抢占端口、不清数据卷、不泄露密钥。
- “我的收藏”三个接口完成真实闭环并保留报告。

### M1 完成标准

- 可以创建、验证和发布不可变测试集版本。
- 可以表达至少一个顺序链路和一个并行层。
- 跨接口变量通过显式提取和映射传递。
- 循环和缺失变量在执行前被拒绝。
- 上游失败时下游真实显示 `SKIPPED` 和阻断原因。

### M2 完成标准

- 多个草稿可以一次调试，日志和结果稳定可读。
- 未通过的精确版本不能采纳为基线。
- 可以执行模块基线、任务基线和测试集回归。
- 失败重跑创建新执行并保留原始统计与 lineage。

### M3 完成标准

- 手动刷新接口后能在激活前看到确定性影响范围。
- 版本比较覆盖源、环境、用例、测试集和执行。
- 关键动作具备脱敏审计历史。
- M0 到 M3 的自动化门禁、浏览器回归和生产真实回归全部通过。

## 15. 实施拆分

该范围不能作为一个超大提交一次完成。实施计划应拆成四组可独立部署、可回滚、可验收的提交序列：

1. **M0 生产收口**：readiness、错误协议、部署校验、迁移和线上闭环。
2. **M1 场景编排**：schema、repository、service、DAG executor、API 和测试集 UI。
3. **M2 执行工作流**：批量调试、基线门禁、回归范围和失败重跑。
4. **M3 影响与审计**：确定性影响分析、版本比较、审计和完整验收。

每组都先写失败测试，再做最小实现，再跑完整 API 测试门禁；任何一组不得以降低既有门禁或隐藏失败为完成条件。
