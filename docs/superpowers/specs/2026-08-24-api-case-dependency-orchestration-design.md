# API 用例依赖编排设计

## 目标

让已经存储在用例版本中的 `dependencies` 和 `extractions` 真正参与执行，使列表、创建、查询等前置用例产生的真实业务标识可以传给后续用例。没有依赖的现有单接口调试、任务执行和基线回归保持原有行为。

## 范围

- 提交执行时递归展开所选用例的依赖，并按依赖优先的拓扑顺序创建执行项。
- 一个依赖用例在同一次执行中只运行一次。
- 依赖用例只有在 `PASSED` 时才向直接依赖它的用例导出变量。
- 只传递依赖配置 `exports` 白名单中的提取变量，不共享其他响应数据。
- 必需依赖未通过时，主体用例不发出 HTTP 请求，记录为 `SKIPPED / dependency`。
- 可选依赖未通过时，主体用例继续运行，但不注入该依赖变量。
- 执行详情标记每一项是用户请求的主体用例还是自动展开的依赖用例。
- 用例编辑器使用按分组组织的用例版本选择器，不再要求手填版本 ID；导出变量从被选用例的提取定义中勾选。

## 非目标

- 本轮不新增“无论主体成功失败都执行”的清理阶段语义。清理仍可作为显式依赖链中的后续用例配置，但 `always-run cleanup` 需要独立的数据模型和调度语义。
- 不自动猜测接口之间的业务依赖，也不批量修改历史用例。
- 不允许跨项目依赖，也不允许通过依赖绕过当前源版本校验。

## 后端设计

`ExecutionService.submit()` 在校验项目、源版本和环境后，递归读取每个用例版本的 `dependency_spec.dependencies`。使用深度优先遍历生成稳定拓扑顺序；同一版本去重，循环依赖直接拒绝提交，展开后总数不得超过 500。

执行快照保留原始 `case_version_ids`，并为展开后的每个版本记录 `role`：`requested` 或 `dependency`。执行表中的 `requested_case_ids` 仍然只保存用户明确选择的用例，执行子项和初始总数使用展开后的集合。

Worker 顺序处理拓扑列表，并在内存中按 `case_version_id` 保存本次结果。执行主体前读取其直接依赖：

1. 必需依赖不存在或状态不是 `PASSED`，生成 `SKIPPED` 结果，不调用 HTTP executor。
2. 已通过依赖只导出配置白名单与实际 `extracted_variables` 的交集。
3. 导出变量与执行请求的全局 overrides 合并；依赖变量优先，确保真实运行时标识覆盖静态占位值。
4. 可选依赖失败只产生事件，不阻断主体。

汇总增加 `skipped`，飞书和前端已有展示兼容。失败分析不处理 `SKIPPED`。

## 前端设计

`CaseEditor` 接收当前源版本的可选用例信息：版本 ID、名称、分组、方法、路径和可导出变量。选择器使用 `optgroup` 按自定义分组或接口目录组织；选中后默认勾选该用例的全部提取变量，用户可以取消不需要的变量。当前编辑版本和已选依赖从候选中禁用，避免明显的自依赖或重复依赖。

原始 JSON 编辑入口继续保留，便于高级用户查看完整配置。

## 错误与安全

- 循环依赖、依赖不存在、跨项目和跨源版本在提交前失败，不创建半成品执行。
- `SKIPPED` 结果只记录依赖版本和状态，不记录任何提取值。
- 依赖提取值继续经过现有脱敏逻辑；未声明在 `exports` 中的值不得进入后续 overrides。
- 超过 500 个展开用例时拒绝提交，避免异常依赖图扩大任务。

## 验收标准

- A 依赖 B、B 依赖 C 时，执行顺序为 C、B、A。
- 多个主体依赖同一前置时，前置只执行一次。
- 依赖提取 `resourceSn` 且主体声明导出后，主体请求收到该值；未声明变量不传递。
- 必需依赖失败时主体为 `SKIPPED`，HTTP executor 调用次数不包含主体。
- 可选依赖失败时主体仍执行。
- 无依赖执行的顺序、参数和汇总不变，只新增 `skipped: 0`。
- 编辑器可按名称和分组选择依赖，并通过勾选配置导出变量。
