# 原测试平台管理体验设计

## 目标

在不改变 Runner、Sonic、Agent 编排和 YAML 数据协议的前提下，让新用户可以从左侧导航完成“准备配置 -> 发起执行 -> 查看历史 -> 处理失败 -> 复核缺陷”的完整闭环，并让长列表和失败反馈保持可理解、可定位、可追溯。

## 设计原则

1. 导航入口必须落到独立状态页，不以自动弹窗或隐式扫描代替页面。
2. 默认展示常用选项，超长模型目录和深度扫描按需加载。
3. 历史列表必须具备搜索、业务状态筛选和有界分页。
4. 外部发送、拒绝、删除等动作保持二次确认；进入页面本身不产生副作用。
5. 服务端保存失败时不修改本地成功状态，不使用伪成功提示。
6. 缺陷草稿与来源执行关联，报告链接指向产生该草稿的执行证据。

## 页面职责

- Agent 工作台：目标、执行策略和当前运行。
- 运行记录：搜索、筛选、分页、轨迹、报告和重试。
- 待我确认：只展示真正需要人工确认的 Agent 动作。
- 执行报告：历史结果、归因、报告链接和失败处理入口。
- 失败分析：有界失败任务列表和修复/缺陷草稿生成。
- 缺陷草稿：复核、复制、拒绝和按应用发送飞书。
- 应用配置：应用、模块、Sonic 和通知目标的聚合状态。
- 群通知：按应用展示通知可用性。
- 执行环境：Runner、设备和 Sonic 绑定，手工触发诊断。
- 环境体检：平台服务依赖检查。

## 数据与安全

- 草稿只保存业务内容和来源标识，不保存 Webhook；提交时从应用配置解析当前 Webhook。
- 草稿状态为 `DRAFT / SUBMITTED / REJECTED / EXPIRED`。
- 只有 `DRAFT` 可提交或拒绝，已结束状态不可覆盖。
- Agent 自动生成只创建草稿，不自动发送。
