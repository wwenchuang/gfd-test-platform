# UI 与 API 通知卡片信息架构设计

## 目标

修复飞书通知中 UI 自动化结果被标成 API 的问题，并让 UI 自动化与 API 测试使用一致、可扫描但互不混淆的信息结构。平台只有一个应用“智小白3D”，“家用”和“共享”作为独立业务维度展示。

## 现状问题

- Sonic/UI 汇总卡片把标题、结论和范围都硬编码为“API 基线回归”。
- API 卡片使用“API 基线测试”，同时把执行类型展示成“任务类型”，测试类型、执行场景和触发方式互相混淆。
- “家用”“共享”项目名被直接当成应用名，应用与业务维度混淆，管理者无法稳定筛选通知。
- UI 卡片缺少测试套名称，API 卡片缺少明确的触发方式，上下游来源不够清楚。

## 展示规范

卡片标题统一使用：`状态图标 应用｜业务｜测试类型｜执行场景+结论`。

- UI 示例：`✅ 智小白3D｜家用｜UI 自动化｜基线回归通过`
- API 示例：`✅ 智小白3D｜共享｜API 测试｜基线回归通过`

正文按固定顺序展示：

1. 结论。
2. 上下文：应用、业务、测试类型、执行场景；UI 可追加测试套，API 追加任务名称、触发方式和环境。
3. 指标：通过率、中文用例统计、执行范围。
4. 异常摘要和解释。
5. 精确指向本次执行的报告入口。

“UI 自动化”和“API 测试”只表示测试类型；“基线回归”“在线调试”“回归测试”“测试执行”只表示执行场景；“手动触发”“定时触发”“任务触发”只表示触发方式。

## 应用与业务

新增纯函数分别归一应用和识别业务，不改变数据库项目名或应用配置：

- `智小白3D APP`、`3D 打印`、`智小白3D` -> `智小白3D`
- `家用`、`智小白3D家用`、`3D家用` -> 应用 `智小白3D`，业务 `家用`
- `共享`、`智小白3D共享`、`3D共享` -> 应用 `智小白3D`，业务 `共享`
- UI 和 API 优先读取用例保存的显式业务；同一执行包含两类业务时显示“家用、共享”。
- 只有未标注的历史用例才使用测试套、模块、项目名等旧数据做兼容展示；新建用例不再依赖名称猜测。
- 未知名称清理多余空白后原样展示，无法识别的业务显示“未标注”。

UI/Sonic 和 API 保持各自的渲染器、Webhook 配置与报告链接生成逻辑，只复用应用与业务展示函数。这样不会把两类通知的权限、发送时机和数据来源重新耦合。

## 验收标准

- UI 卡片 JSON 中不再出现“API 基线回归”或“API 基线测试”。
- API 卡片明确包含“API 测试”，且不会出现“UI 自动化”。
- UI/API 卡片均明确展示应用、业务、测试类型和执行场景。
- API 定时任务显示“定时触发”；基线回归不再被错误展示为任务类型。
- 家用和共享卡片的应用均显示“智小白3D”，业务字段分别显示“家用”“共享”。
- 既有失败归因、通过率语义、Sonic/Midscene 报告按钮和 API 精确执行报告链接保持有效。
