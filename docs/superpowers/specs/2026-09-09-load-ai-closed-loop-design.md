# AI 参与与平台约束：压测完整验证流程

## 目标

让每轮压测回答“验证了什么、证据够不够、下一步具体做什么”，并能从建议进入正确配置、通过预检、执行、停止、形成报告。下一轮建议不限于升压。AI 无法完成分析不阻断确定性报告，也不能绕过平台门禁。

## 分工

| 环节 | AI 的职责 | 平台的职责 |
| --- | --- | --- |
| 测试设计 | 理解目标、业务链路、失败步骤与观察重点；提出可比较的曲线和排查顺序 | 校验场景动作、副作用、测试账号/清理、参数结构、版本和目标地址 |
| 执行准备 | 解释配置差异与预计风险；指出缺少的证据 | 重新核对每个节点容量与连通性，单用户执行真实断言，检查监控，冻结环境/场景/阈值/停止策略 |
| 运行 | 不直接改写运行中的压力或判断停止 | k6 按冻结曲线发压；平台负责幂等启动、节点屏障、指标接收、人工/错误保护停止与终态恢复 |
| 报告 | 基于证据解释可能原因，提出下一轮验证假设和方案 | 确定性计数、延迟、阈值、阶段达成、证据完整性和服务资源归属；缺失与零值分开 |
| 下一轮 | 给出完整可审阅方案；允许保持压力、稳态观察、降压恢复、拆分失败步骤及有界升压 | 校验每段压力/时间、起点、单位、VU预算、业务目标与风险；保留原提案和调整原因，用户确认后仅创建草稿 |

## AI 输入

输入均来自同一执行的冻结快照和结构化报告：测试目的、原完整 workload、业务目标与允许增长/观察上限；每阶段计划/实际负载、采样覆盖与节点分片；HTTP/业务/完整链路失败和最慢步骤；被测容器 CPU、working set、配额、真实实例标签与样本覆盖；压力机资源独立列示。外部响应正文、令牌和页面指令不进入模型指令。每个结论引用现存 evidence_id。

缺证据需明确：未采集、过期、阶段未对齐、配额未知、节点缺失，均不能按零错误或零资源占用处理。CPU 两分钟 rate 不能证明短阶段瞬时峰值；报告保留采样时间和口径。

## 输出和状态

每次先给一个主要行动计划，再用有顺序的建议说明前置排查和验证方法。配置使用与执行编译器一致的 workload：executor、start_vus/start_rate、time_unit、stages、pre_allocated_vus/max_vus。不再用一个目标数字替代阶段曲线。target 与总时长仅作为从完整曲线导出的摘要。

建议来源状态独立于能否执行：

- AI 建议已通过校验：保存原建议与最终配置，参数完整合法且符合当前证据边界。
- AI 建议被调整：保存原建议、具体越界字段/原因、最终配置和前后差异，不能冒称原 AI 参数已被采纳。
- 规则备用建议：AI 超时、格式或证据引用纠正后仍失败时，提供确定性排查/原曲线复验方案；基础报告继续可用。

行动状态分为：可配置复验、需补证据、需先修复、已完成本轮目标。暂不升压但仍需验证必须有明确行动，不能等同没有后续工作。

## 校验层次

1. **硬门禁**：身份/应用范围、原目标与版本、编译器字段白名单、有限数值及总时长、节点硬上限/校准、单用户预检、生产确认、不可扩大凭据/网络权限。任何 AI 输出不能改变。
2. **证据约束**：存在业务/链路/延迟失败，先排查并保持原配置复验；未达压先核对阶段证据和计算；服务/节点资源异常先排查归属；监控不足先补采集。不得以低 CPU 单独推导容量。
3. **方案空间**：证据完整且目标明确时，AI 可在用户允许的逐阶段增长、观察时长和原 VU 预算内提出参数，保留升压、稳态、恢复顺序。平台验证提案，不用单一固定公式覆盖所有有效提案。阶段扩展或拆分场景需要可见的配置差异并再次准入，不能自动执行。

结构不完整时先进行一次带错误原因的模型纠正；仍失败使用备用计划。建议与实际运行参数、阈值、停止条件均须可追溯。旧诊断保持原记录，重新诊断使用新提示词版本；不会重新压测。

## 怎样定位性能瓶颈

平台需分别回答容量边界、直接限制因素与根因验证。找到吞吐不再增长/P95恶化的拐点，只能说明限制出现；单项资源高并不足以证明唯一根因。

| 候选限制因素 | 需要对齐的证据 | 后续证伪或确认实验 |
| --- | --- | --- |
| 服务 CPU / CPU 配额 | 实际核数、quota、节流时间、同阶段延迟/吞吐、热点调用 | 固定其他条件，降低计算型接口占比或在获准后调整CPU配额，比对拐点是否移动 |
| 内存 / GC / 泄漏 | working set/堆、配额、GC暂停、分配速率、OOM/重启、降压后基线 | 相同压力延长观察，对比资源是否持续增长与降压后是否回落；不能凭单次内存峰值称泄漏 |
| 应用线程池 / 连接池 / 队列 | 活跃/最大/等待数、队列长度、拒绝数、等待时间、线程或trace采样 | 固定压力，拆分等待步骤；有配置授权后单独调整池上限并复验 |
| 数据库 / 锁 / 慢查询 | 同实例数据库连接占用/上限、等待、锁、慢SQL、缓存命中、查询trace | 复现具体查询与数据规模；分别验证索引/锁冲突/连接池假设，不把连接多直接称数据库瓶颈 |
| 网络 / 磁盘 | 带宽与上限、重传、连接/TLS等待、磁盘利用率/队列/延迟及实际设备 | 区分压力机到服务网络、隧道、存储、下游链路，保留路径并做对照 |
| 下游依赖 / 限流 | trace子调用耗时、超时、429/限流指标、依赖服务队列 | 单接口与完整链路对照；获准后使用隔离桩或依赖侧观测验证 |
| 发压端容量 / 脚本 | 各Agent实际到达率、VU、CPU/内存、丢弃迭代、阻塞步骤 | 同总压力分给更多节点，验证目标是否恢复；不能归因给被测服务 |

每项输出必须有 `已支持 / 待验证假设 / 证据缺失 / 本轮不适用` 之一、影响阶段/接口、引用证据、相反证据及下一步。`已支持` 指当前证据支持限制因素；代码级根因需要日志、trace或对照复验，不把相关性写成因果性。多个瓶颈可同时存在，修复第一处后再测下一处。

上述是诊断产品的目标契约。本批先落地独立的九类“证据覆盖”清单，状态为 `available / partial / missing`，配有证据引用、限制和下一步补采；这不是九类根因已经验证。现有 AI 继续提供有证据引用的定性分析。逐阶段候选根因、反证、验证实验关联及跨轮容量区间的结构化持久化尚待后续实现，不能把覆盖清单当作这些能力已经交付。

当前实现有 HTTP/业务链路统计、各Agent资源、主机CPU/内存/网络/磁盘、容器CPU/working set、Pod状态和PostgreSQL基础连接/事务模板；演示实际只接入自身容器CPU/内存。尚没有应用线程/连接池、GC、SQL锁与trace端到端采集，必须标记缺口，不能声称已经支持所有根因定位。

## 实验设计与结束条件

1. **基线**：确认真实目标、拓扑、节点、配额、监控采样和测试数据；低负载验证业务断言及清理，记录空闲资源与响应基线。
2. **寻找拐点**：优先使用固定/阶梯到达率控制业务链路每秒发起量；每次升压后安排保持段。并发模型用于用户占用/并发场景，不把VU视作固定RPS。
3. **缩小范围**：首次出现持续阈值失败、吞吐平台、队列增长或资源限制后，不继续盲目加压。记录最后完整通过与首次失败的压力区间，用区间内中间压力及重复稳态实验确认可重复性。
4. **验证原因**：按慢步骤与资源时间相关性排候选，只改变一个影响因素或隔离一个步骤，保留版本/数据/环境/阈值；AI写明预测“若此假设成立，哪个指标应怎样变化”。
5. **恢复与稳定性**：降回基线压力，检查错误、延迟、队列和内存恢复；必要时在低于拐点的压力下做长稳态，不将短跑外推到长期。

每阶段保持时间需覆盖监控聚合窗口并提供足够独立样本。当前CPU使用两分钟rate，15秒阶梯只能用于流程点检；用于资源归因的保持段应超过此窗口且保留前后观察。具体时长、步长、最高压力和可接受损伤由目标服务和用户授权边界决定，不把示例值当生产默认。

停止条件包括现有HTTP错误保护和人工停止；服务CPU/内存/队列等告警尚未自动联动，设计或报告不得把它们写成已实现保护。演示在既有0.5核/256MiB容器限制和有界接口内验证，不能把目标宿主机耗尽作为成功标准。没有触达瓶颈时报告“已验证至本轮最大压力，瓶颈未触达”；有外部限制或样本不足时报告“本轮无法判断”。

## 后续交付顺序与准入

1. 部署本批完整曲线与来源校验，用 Safari 完成两份旧阶梯报告重新诊断到草稿、预检和有界复验；无需重跑已通过的家用基线。
2. 补齐演示双节点、可预期错误、人工停止、HTTP 错误保护停止及全部节点终态。单节点历史证据不替代双节点证据。
3. 校正阶梯达成计算与采样边界，形成足够长的保持段和低负载恢复段；短阶段平均值不进入容量结论。
4. 接入应用运行时/连接池、SQL/锁等待和 trace，记录目标拓扑与实例归属。只有有对应证据的领域才能升级为具体瓶颈候选。
5. 建设跨轮实验记录，绑定父执行、假设、单一变量、预测、观察结果和反证，再计算“最后稳定—首次持续失败”区间。对照复验通过后才发布瓶颈结论。

第 3—5 步是后续实现与线上验收工作，本批没有宣称完成自动寻优、全部根因诊断或资源告警自动停止。

方法参考：[Grafana k6 API 压测指南](https://grafana.com/docs/k6/latest/testing-guides/api-load-testing/)、[自动化性能测试与停止](https://grafana.com/docs/k6/latest/testing-guides/automated-performance-testing/)、[OpenTelemetry 可观测性与跨服务追踪](https://opentelemetry.io/docs/concepts/observability-primer/)。具体实验参数仍以本项目可观测性和授权环境为准。

## 实现验收矩阵

测试同时覆盖四模型、分钟单位、零目标恢复阶段、起始压力大于阶段目标、阶段时长与总量一致、超上限/NaN/不完整提案、保留所有阈值/监控/停止策略、AI 正常/调整/备用三条路径。Safari 验收从真实报告到曲线对比、配置、节点、预检和启动，各步骤给出明确失败原因。双节点执行按全局目标分片，停止后每节点终态、尾部指标和报告对应。演示目标与监控必须属于同一隔离服务，压力机数据不得代替服务数据。

执行历时与用例累计耗时分别计算和展示：前者是运行起止时间差，后者为所有用例的耗时之和；并行执行时可大于历时，缺时间戳不得互相替代。
