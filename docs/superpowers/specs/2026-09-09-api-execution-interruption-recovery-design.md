# API 执行中断收敛设计

## 问题与证据

每日基线执行 `f08274df-b04c-4874-9634-29bf9da879da` 已完成 219/288，随后长期保留为 `RUNNING`。线上日志确认 `midscene-api-worker.service` 在 2026-09-09 15:30:22 收到 Warm shutdown，并于 15:30:24 重启。当前执行器只允许 `QUEUED → RUNNING`，新 Worker 不会接管数据库中已经是 `RUNNING` 的执行，因此记录不会自行结束。

## 行为设计

平台不得自动重放这类任务的未完成请求，因为基线可能包含创建设备数据、切换设备、发验证码等副作用。恢复动作只负责收敛状态：已经终态的用例保持原结果；仍为 `RUNNING` 或 `QUEUED` 的用例写入一条脱敏的 Worker 中断结果；执行汇总转为终态，并记录可读的中断事件。用户可以随后从执行记录按原范围重新运行。

Scheduler 每轮扫描长期没有进度的 `RUNNING` 执行。安全静默窗口默认 300 秒，可通过 `API_TESTING_EXECUTION_STALE_SECONDS` 在 120 至 3600 秒之间调整。最后进度取执行记录、全部子用例更新时间和执行事件时间的最大值；窗口内仍有步骤事件或结果进度的任务不处理。实际收敛时再次加锁并复核时间，重复派发和并发扫描保持幂等。

## 数据与通知

不新增表或迁移。中断的子用例沿用 `BROKEN` 和 `worker` 分类，错误文案固定为“执行 Worker 中断；已完成结果已保留，未完成用例未自动重放”，不包含异常、请求或凭据。执行事件记录 `failure` 和 `execution_finished`。收敛后刷新关联任务；原本允许飞书通知的定时或基线任务继续发送终态报告。

## 验收

- 旧执行中已通过的用例结果和尝试记录不变。
- 静默超过阈值的 `RUNNING` 执行转为 `DONE`，剩余用例为 `BROKEN`，汇总总数不变。
- 刚有进度的执行不被收敛。
- 同一执行被重复恢复只成功一次，不产生重复尝试。
- Scheduler 只派发超过阈值的执行；Worker 完成任务刷新与通知。
- 部署后旧的 219/288 执行不再无限显示“执行中”，页面明确展示中断证据并保留重跑入口。
