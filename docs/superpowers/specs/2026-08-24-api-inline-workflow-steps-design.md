# API 用例内编排步骤设计

## 目标

让单个 API 用例完整表达并执行“前置步骤 -> 主体请求 -> 清理步骤”，解决动态业务参数依赖固定 ID、用例之间难以独立运行、打印下发后未取消等问题。已有跨用例依赖继续用于登录、设备初始化等可复用流程；仅服务当前用例的查询、创建、状态变更和回收动作放到用例内部。

## 范围

- 用例支持有序前置步骤和有序清理步骤。
- 前置响应提取的变量可传给后续前置、主体和清理步骤。
- 主体响应提取的变量可传给清理步骤。
- 前置失败时不执行主体请求。
- 清理步骤按 `always-run` 语义执行，只回收本次用例创建或启动的数据。
- 执行报告按前置、主体、清理三个阶段展示请求、响应、断言和提取变量。
- 打印下发类用例必须配置取消打印清理步骤，未配置或取消失败时不能成为有效基线。
- 长期 Token、Authorization、Biz 等认证信息只从环境运行时注入，不写入用例、代码、日志或报告。

## 数据结构

复用 `api_case_versions.processing_spec` JSONB，不增加数据库迁移。保留已有 `pre`、`post` 变量处理动作，并扩展两个字段：

```json
{
  "pre": [],
  "post": [],
  "setup_steps": [
    {
      "name": "查询可用模型",
      "enabled": true,
      "request": {
        "method": "GET",
        "path": "/print3d/api/v1/model/page",
        "service": "default",
        "path_params": {},
        "query": {"pageNum": 1, "pageSize": 20},
        "headers": {},
        "cookies": {},
        "body": null
      },
      "assertions": [
        {"type": "status_code", "operator": "equals", "expected": 200, "timeout_ms": 0, "enabled": true},
        {"type": "json_path", "operator": "equals", "path": "$.code", "expected": 0, "timeout_ms": 0, "enabled": true}
      ],
      "extractions": [
        {"target": "modelSn", "type": "json_path", "path": "$.data.list[0].modelSn", "required": true}
      ],
      "required_variables": []
    }
  ],
  "cleanup_steps": []
}
```

每类步骤最多 20 个。步骤名称在同一阶段内必须唯一。请求、断言和提取规则复用主体用例的严格解析器；不允许步骤自带 `data_rows`、嵌套依赖或嵌套步骤。`required_variables` 用于控制可执行性，缺少变量时记录为 `SKIPPED`，不发送不完整请求。

## 执行语义

1. 合并执行覆盖值、首个启用数据行和跨用例依赖导出变量。
2. 执行原有 `processing.pre`。
3. 按顺序执行启用的 `setup_steps`。每一步通过断言后，将提取值合并到工作流变量。
4. 任一必需前置失败时，主体标记为 `SKIPPED`，进入清理阶段。
5. 使用累计变量渲染并执行主体请求。主体提取值合并到工作流变量。
6. 执行原有 `processing.post`。
7. 在 `finally` 语义下按顺序执行启用的 `cleanup_steps`。清理阶段不因普通主体失败或用户取消而省略；单步仍受总请求超时约束。
8. 清理缺少 `required_variables` 时记录 `SKIPPED`；其他清理继续执行。
9. 主体通过但清理失败时，最终结果为 `FAILED / cleanup`。主体已失败时保留主体失败分类，同时在报告中单独标红清理失败。

Worker 进程被强制终止时无法保证进程内 `finally` 执行。报告必须显示清理未完成，后续可由重跑清理步骤或资源回收任务处理，不能把该次结果采纳为基线。

## 打印安全规则

- 生成器从同一接口版本中查找语义为“取消打印/取消任务/停止打印”的接口，不硬编码生产 URL。
- 打印下发请求必须从真实响应提取 `printSn`、`printTaskSn`、`taskId` 等取消接口必填标识，具体 JSONPath 依据响应 Schema 或示例推导。
- 取消打印清理步骤声明这些标识为 `required_variables`，仅取消本次主体请求返回的任务。
- 无法唯一定位取消接口或无法推导任务标识时，生成预览保留明确阻断项，不允许保存为有效基线；用户可在编辑器补全映射。
- 取消请求必须同时校验 HTTP 状态、业务码和关键业务结果。取消失败时整条用例不得通过。

## 前置步骤设计原则

- 优先调用列表或详情接口动态获取当前账号可见资源，不依赖固定数据库 ID。
- 创建型前置必须同步增加与之对应的清理步骤。
- 收藏场景采用“添加 -> 查询存在 -> 取消 -> 查询不存在”；清理只处理本次添加的收藏。
- 模型、切片、打印等生命周期使用上一步真实响应提取的标识。
- 不可逆操作（积分兑换、账号注销等）默认不自动编排进定时基线。
- 设备设置类用例先读取原值，主体修改，清理恢复原值。
- 登录和设备初始化若被多个用例共用，继续使用已有独立用例依赖，不在每条用例重复。

## 按接口特性生成

生成器先结合目录、标签、摘要、方法、路径、请求 Schema、响应 Schema 和同版本接口关系识别接口特性，再选择编排策略。仅凭 `GET/POST` 或名称单个关键词不足以自动生成破坏性步骤。

| 接口特性 | 前置策略 | 主体断言 | 清理策略 | 基线准入 |
| --- | --- | --- | --- | --- |
| 只读列表/配置/枚举 | 通常无前置 | 业务码、数据类型、分页结构或关键枚举字段 | 无 | 可直接准入 |
| 详情/状态查询 | 先调用同资源列表并提取首个有效 ID | 业务码、返回 ID 与请求 ID 一致、关键字段存在 | 无 | 列表为空时跳过并标注缺少种子数据 |
| 新增/上传/创建 | 先查询重名或配额，必要时生成本次唯一名称 | 返回创建标识、查询可见 | 删除本次创建资源并查询不存在 | 无可靠删除接口时默认不进定时基线 |
| 修改/重命名/设置 | 先查详情并保存原值 | 修改后详情与目标值一致 | 恢复原值并二次查询 | 无法读取原值时禁止自动修改 |
| 删除 | 前置创建专用临时资源 | 删除成功且查询不存在 | 无，或幂等兜底删除 | 禁止删除列表中碰巧存在的历史数据 |
| 收藏/关注/点赞 | 先查询当前状态，必要时构造未收藏资源 | 状态变更且查询可见 | 恢复执行前状态 | 清理必须恢复，不固定假设初始状态 |
| 异步任务 | 创建或选择可执行输入 | 返回任务 ID，轮询到业务完成态并校验产物 | 取消未完成任务、删除测试产物 | 超时、未知终态或无取消能力均不通过 |
| 切片 | 动态选取可切片模型和在线设备 | 切片任务成功、产物地址/标识有效 | 删除本次切片产物 | 只使用本次提取的模型/切片标识 |
| 打印 | 动态获取在线专用设备和有效切片结果 | 下发业务成功并返回打印任务标识 | 必须取消本次打印并确认非打印态 | 取消缺失或失败时硬阻断 |
| 设备控制/参数设置 | 查询在线状态、能力和原始设置 | 指令业务受理，并在状态接口确认生效 | 取消动作或恢复原设置 | 设备离线、能力不支持时跳过，不伪造成功 |
| 文件上传/生成 | 准备长期测试素材并校验格式大小 | 业务码、文件标识、可访问性或处理状态 | 删除本次上传文件/任务 | 临时签名 URL 不能长期固化 |
| 登录/验证码/第三方授权 | 使用可刷新测试凭证或独立依赖 | 登录态与用户身份字段 | 注销临时会话 | 短期 Token、短信、微信正式账号不做固定基线 |
| 不可逆/高成本 | 不自动生成执行链 | 仅保留契约或人工验证项 | 不适用 | 积分兑换、账号注销、真实扣费等默认排除 |

匹配结果必须带 `workflow_kind` 和生成说明，无法唯一识别资源关系时保留为待完善预览，不自动落成有效基线。用户手工调整后的步骤仍走相同的严格校验和清理门禁。

## 报告与界面

编辑器按顺序展示三段：前置步骤、主体请求、清理步骤。步骤支持从当前接口资产选择后自动填入方法和路径，也支持编辑参数、请求体、断言、提取及必需变量。报告将每个步骤显示为可折叠行，阶段、状态和失败原因始终可见。

## 验收标准

- 前置提取变量能传到主体和清理请求。
- 前置失败阻止主体，但已具备变量的清理仍执行。
- 主体断言失败后清理仍执行。
- 主体成功而清理失败时最终结果不通过。
- 打印下发成功后取消请求被执行，且使用本次下发返回的任务标识。
- 所有步骤请求、响应和提取值经过现有敏感信息脱敏。
- 旧用例没有 `setup_steps` / `cleanup_steps` 时行为保持不变。
