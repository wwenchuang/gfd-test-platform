# 性能测试统计分析建设计划

> 执行方式：后续采用 executing-plans 按任务实施；本稿是基于公司现有附件的规划，不代表功能已经实现。详细接口契约与数据库迁移在各阶段开始前补齐。

**目标：** 将一次执行的数据、多轮压测对比、优化验收和应用性能覆盖沉淀到平台，自动形成可追溯的领导汇报报告。

**架构：** 保留现有 k6 Agent、运行记录和耗时分桶。在其上建立压测计划、阶段统计、监控证据、对比组与正式报告快照；汇总页引用执行证据，不复制维护另一套结果。历史导入与原生采集分开标识。

**技术基础：** 当前 Python 服务、PostgreSQL、Vue、k6 Agent；监控集成复用公司已有系统，具体接入方式待核实，不预先要求新增一套监控基础设施。

## 全局约束

- 附件中的旧配置和结论仅作参考，不自动写入当前环境或采纳为基线。
- 用中文标签说明 VU、RPS、TPS、P95 等概念；请求成功、断言成功、真实业务完成分别统计。
- 没有数据为未知，不能填 0 或判定通过。0 次失败和无失败率样本分开。
- Agent 的发压能力不等于被测服务容量；发压机监控不能代替被测服务监控。
- 真实打印等写操作压测必须使用明确授权的测试资源和清理方案；不得复用历史日常回归授权直接高并发操作生产设备。
- 当前排除 EP one、京东、设备首次绑定和共享商城完整写链路。附件中的其他业务仅用于借鉴统计结构，不能扩大任务范围。
- 所有阶段分别记录代码验证、样本验收、部署与真实运行结果。

## 参考材料及发现

### 业务接口压测覆盖.xlsx

Sheet1 的 A1:P29 有业务内容：14 个不同接口、两组配置共 28 个接口条目；26 条填写了采样结果，第 17、20 行没有结果。不能将重复压测轮次算成接口覆盖数量；没有应用接口总清单和纳入范围，不能计算全量覆盖率。

配置从 1C/2G × 1 变为 2C/4G × 5，并发也从 20/50 变为 50/100。结果可以说明不同环境容量表现，但不能把 TPS 差值直接称为代码优化收益。

设备绑定记录 F6=65354、G6=55335：若 KO 确认为失败请求数，失败率约 84.67%。平台应自动计算并突出显示，但需核实旧表 KO 定义和断言方式。多条 P90/P95/P99 完全相同，不能直接判为错误；应保留来源、精度，必要时核对原始 JTL。

### 迁移鉴黄压测报告.docx

包括背景、数据流向、环境、阶梯摸底、优化前后结果、监控和问题清单。正文同时包含嵌入的 Excel，已读取其真实单元格。

优化前 50/100 并发，TPS 25/23、平均耗时 1500/2700 ms；优化后正文表格为 200 并发、TPS 625、平均耗时 312 ms。不同并发与限流策略下不能直接形成纯优化倍数。

报告描述超过 100 QPS 时直接返回成功。其 625 TPS 不能据此认定为真实鉴黄处理能力。需要记录审核完成、跳过/降级、限流、排队与实际依赖调用量；如现有响应无法区分，需要服务日志、追踪或业务埋点作证。

### 压测报告模板.docx

章节覆盖术语、概述、环境、负载与稳定性、监控、分析、结论和风险，适合作为正式报告骨架。模板含具体 WPS 示例，并非所有内容都可原样套用。

嵌入表：10 并发 TPS 12.6、平均 758 ms；20 并发 TPS 14.4、平均 1335 ms、216/2928 错误。可辅助识别加压后吞吐增益有限、耗时和错误升高，准确瓶颈仍需对齐资源与日志。

稳定性表记录 23079 次请求、3 次错误，却填错误率 0；按失败请求口径应为约 0.0130%。正文称每轮 5 分钟，但部分样本数/TPS 推算时长与此不一致，旧结果导入必须允许“时长待核实”，不得补造时间线。30 分钟是这个案例的时长，不定义为所有业务统一的稳定性验收时长。

## 现状与首要缺口

已核对 `task_server/api_testing/services/load_report_service.py`：已有平均耗时、P50/P90/P95/P99、最大耗时、请求/业务/链路计数、5 秒窗口、步骤统计和基础历史对比。

需先解决：

- `_load_goal` 当前并发模型依据目标 VU 和有效迭代判断 reached，并没有用逐时段实际 VU 证明并发持续达到目标。
- 阶梯到达率需要按各阶段目标积分和实际发起量验收，不能用 start_rate 或全程平均替代所有阶段。
- RPS 当前优先使用配置时长计算；需保留计划时长、实际活动时长及计数起止，明确终止、预热、冷却和阶段统计的分母。
- 当前基本历史对比不能替代可人工选定的优化前后对比组，也不能直接跨场景版本量化优化收益。
- 被测服务 CPU/内存、数据库、磁盘等监控需独立验证接入覆盖，不能以校准资源采样宣称已具备。

## 建议的功能组织

主层级：应用 → 压测计划 → 场景及版本 → 执行轮次 → 阶段 → 步骤及指标。

- 性能场景：管理可复用脚本及版本。
- 压测执行：单次操作及运行状态。
- 性能报告：单次证据、阶段结果和明细。
- 统计分析：按应用、版本、环境、时间查询覆盖、性能趋势和多轮对比。
- 正式汇报：从一个压测计划选择执行轮次，形成有版本和审核记录的总结。

统计分析页默认当前应用、最近周期；首屏显示核心接口覆盖、存在风险的场景、回退指标和未关闭问题，避免“累计执行次数很多”掩盖覆盖不足。详情支持下钻到原始执行、阶段、接口与失败证据。

## 阶段一 统计口径与采样可靠性 P0

涉及 `load_report_service.py`、`task_server/api_testing/models/load_testing.py`、`load_agent` 的指标采集/上报实现以及对应服务和 Agent 测试。先定位现有采集入口，不大规模重构。

- [ ] 定义并版本化指标字典：requests、HTTP failures、business assertions/failures、workflow completed/failed、降级与跳过、dropped iterations。
- [ ] 增加实际 VU 时间序列、阶段标识、窗口实际起止与有效时长；核实是否已有兼容字段，优先复用。
- [ ] 明确 RPS=请求数/有效秒数；TPS=定义好的事务完成数/有效秒数，区分成功事务 TPS 和含失败的完成 TPS；一次链路多个请求时不能混用。
- [ ] 失败率按失败数/对应样本数计算；不平均各节点失败率。分位数合并原始分桶后计算，不平均各节点 P95；精度/算法版本写入报告。
- [ ] 实际并发和到达率按阶段判定，规则在页面配置并冻结到执行快照。短跑、提前停止和部分节点缺失不能误判目标已达成。
- [ ] 平均、最小、最大等指标注明可用性；最小值无原始采集不能从分位数猜测。
- [ ] 编写回归测试：零样本、3/23079、节点样本不均、阶段变更、实际 VU 不足、提前停止、分桶不一致；先失败再实现，再提交。

验收：报告、导出与原始计数一致；目标不足不能通过；不存在缺失数据被补零的图或统计。

## 阶段二 压测计划与多轮结果 P1

新增独立计划/轮次管理服务和页面，关联现有 scenario_version、run、environment_revision；不把多次运行复制成同一条可变记录。

- [ ] 页面填写应用、业务版本、负责人、背景、目的、范围、准入阈值、负载类型、时间、数据集和资源快照。
- [ ] 支持摸底、容量、稳定性和回归计划；一个计划容纳优化前、优化后、复验等轮次。
- [ ] 自动生成附件同类结果表：阶段并发/实际并发、时长、Samples、KO/失败率、平均/P90/P95/P99/最大、RPS、事务 TPS、业务有效吞吐。
- [ ] 保留稳定阶段选择规则，预热/冷却/异常期间单独显示；不能静默剔除错误数据改善结果。
- [ ] 联合时间轴显示实际 VU、吞吐、响应时间、错误率，图表缩放与悬停同步。
- [ ] 测试计划编辑、复制、归档、历史快照及数据清理；归档场景不能破坏历史报告。

验收：一个计划至少覆盖三个负载阶段和两轮执行，能逐格追溯数据，且实际 VU/请求/事务不会混为同一指标。

## 阶段三 监控关联与优化验证 P1

新增独立监控适配层和对比服务，报告组件只消费统一数据；监控接入采取只读、按环境授权。

- [ ] 先支持上传带时间和来源的监控截图/日志作为证据，再对接已有 Prometheus/Grafana/云监控之一。
- [ ] 区分发压节点与被测应用；采集被测服务 CPU/内存、实例数、重启/OOM，按实际依赖扩展数据库连接/慢查询、磁盘 I/O、网络、队列和限流。
- [ ] 保存时区、采样间隔、单位与 CPU/内存分母，缺失监控明确显示未接入或采样缺口。
- [ ] 支持人工选择 A/B 轮次；自动列出环境资源、应用版本、数据集、负载、时长、阈值、脚本差异。
- [ ] 同条件测试展示数值差与变化率；硬件/Pod/并发不同仅作实验对照，不输出“代码性能提升多少”的因果结论。旧值为零时不除零。
- [ ] AI 引用具体窗口、接口和监控证据，分开事实、推测、建议验证；无日志不直接宣称 SQL 或内存泄漏根因。
- [ ] 建立问题 → 负责人 → 修改说明 → 复验执行 → 关闭依据；不自动把 AI 建议标成问题已解决。

验收：对齐一组资源与性能曲线；演示同条件可比、异配置不可直接归因；报告可追溯一个优化问题的复验记录。

## 阶段四 覆盖统计与性能回归 P2

- [ ] 从应用接口资产选定纳入范围、重要级别和豁免原因；以接口唯一标识去重，固定统计时点和范围版本。
- [ ] 同时显示资产覆盖率、核心接口覆盖率、满足时效及验收条件的有效覆盖率；单接口测试不代替核心链路覆盖。
- [ ] 接口 × 场景类型矩阵：未覆盖、无结果、已测待复验、达标、存在风险、结果过期；关联最近可信执行。
- [ ] 人工采纳证据完整、达到负载且符合标准的执行为性能参考基线，记录场景/资源/环境快照；自动修复重跑不混入固定基线。
- [ ] 按周/月观察同条件 P95、成功 TPS、失败率和容量退化；失败/终止记录保留，防止仅挑好结果。
- [ ] 页面配置回归频率、阈值、连续异常策略、静默期与接收人；基线 API 每日功能回归不等于每天高强度压测。
- [ ] 专用节点优先，允许配置本机参与、时间窗和容量；实际生产压力另行控制。

验收：导入附件后识别为 14 个唯一接口、28 个轮次条目、26 条有结果；不得在没有总资产分母时展示全覆盖百分比。可从覆盖矩阵跳到执行报告并看到回归异常与去重告警。

## 阶段五 正式汇报与历史导入 P2

- [ ] 首页领导摘要为一页：测什么、是否达标、经验证的容量范围、未解决风险、建议；技术表格与证据放后面，术语为附录/提示。

- [ ] 支持 Word 汇报稿和 Excel 覆盖表导出，HTML 详情保留交互。发送飞书由用户触发或明确已授权策略控制。

## 测试与实施节奏

每阶段先补失败测试，再做最小实现，专项通过后进行真实浏览器操作验收、更新 CODEX_STATE.md 并独立提交。服务端测试覆盖计数与聚合；前端测试覆盖筛选、图表、缺失、导出和状态；真实验收按授权环境实施，不以样本截图代替真实容量结果。

推荐顺序：阶段一 → 阶段二 → 阶段三 → 阶段四 → 阶段五。历史资料导入预览可与阶段二一并设计，但不能先导入成可信自动化基线。阶段二结束即可形成第一版可用统计报告，阶段三结束具备优化前后验证能力；不应等待所有看板做完才交付。

## 需要业务侧确认的数据
